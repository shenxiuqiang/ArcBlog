## 0. 一句话结论

归档期的**需求格式**比归档期的**文档形态**健康得多：`REQ-030`/`REQ-032`/`REQ-034`/`REQ-041` 已经写出了「可执行命令 + 负例 + 零改动逐字节比对 + 受限未验证」的成熟范式
（v1 期三条需求文档的对应段落），可以**整段继承**；
失败的是**外壳**——一个文件同时承载需求、探针报告、Dev 自证、逐批追加与轮末裁决（v1 期需求 `REQ-019` 585 行、`REQ-030` 550 行），
以及**没写完就落笔的验收标准**（`REQ-030:167` 字面口径在轮末被 PM 自己推翻、v1 期 `REQ-002` :94 的写入类断言连续三轮「受限未验证」）。
Stage 2 的规范要点 = **继承判据写法，重建载体形态**：一条需求一个条目、状态与证据同一动作、总览由正文算出。

## 1. 需求条目模板

### 1.1 总表表头（`docs/02-产品需求/` 的主表，一行一条；放**可机检列**）

```text
| 编号 | 标题 | 领域 / 能力 | 来源追溯 | 状态 | 阻塞原因 | 优先级 | 验收标准(编号) | 平台边界 | 依赖 | 写范围 | 证据 | 验证人·日期 | 基线 commit | 未覆盖范围 |
```

长文（背景、探针、逐条验收、结果）一律进**条目正文**，总表只留指针与短列；总表**不得**出现 >2 行的单元格（治 A5： 曾出现 1561 字符单行）。

### 1.2 字段定义（12 个字段，均必填；「否」也要写「无」）

| # | 字段 | 取值与格式 | 校验 |
| - | --- | --- | --- |
| 1 | **编号** | `PRD-<领域码>-<NNN>`，三位递增、**永不复用** | 全局唯一；与 归档的 `REQ-NNN` **不混用**（见 §3.1） |
| 2 | **标题** | 一行，写「给谁 + 什么能力 + 什么可观察结果」 | ≤40 字；不含变更史、不含轮次号 |
| 3 | **领域 / 能力** | `D<n>.<m> 领域 / C<n>.<m> 能力`，来源 = `02-产品需求/` 自己的领域表 | 领域码必须在领域表内 |
| 4 | **来源追溯** | `docs/01-产品概念/0X §n` 或 `J<n> 步骤 <k>`（`docs/01-产品概念/03-使用旅程.md` 的旅程编号）或归档缺陷号 | 锚点必须可解析；**禁止**指向 的**规则**（只引事实） |
| 5 | **状态** | 六态单列：`未开工｜开发中｜已实现待验｜已验证｜平台边界｜已废弃` | 六值之一（词表见 §3.3，源自 `S1-04 §4` / `docs/README.md:132` 家族） |
| 6 | **阻塞原因** | 正交列：`无｜待决策｜待批准｜待平台能力`；`待决策/待批准` 必须写决策人 | 四值之一；**不得与状态混写在同格**（治 把 🟡 同时当三义） |
| 7 | **优先级** | `P0｜P1｜P2｜P3`；未拍板写 `【决策待定】` + 候选 A/B + 裁决人 | 归档口径沿用 （P0 门禁红/越权，P1 功能错，P2 体验，P3 建议） |
| 8 | **验收标准** | 每条 = `可执行命令` 或 `可观察行为` **之一**；带编号 `A1…An`；必须含 **证据形态** 与 **≥1 条负例** | 结构断言：每条含 `命令：` 或 `可观察：`；全集含 ≥1 个「负例」 |
| 9 | **平台边界** | 引用 `docs/05-开发文档/` 平台边界篇的条目号；无则写「无」 | 出现「平台不支持」字样时必填（归档证据 `docs/05-开发文档/附件/arc-contracts.md`） |
| 10 | **依赖** | 前置需求号 / 外部条件 / `blocked_by` 任务；**验收所需的外部条件必须写在这里** | 有前置未满足 ⇒ 状态不得越过 `开发中` |
| 11 | **写范围** | 允许写的路径 + 绝不写的路径（照 `REQ-030:227`） | 两两侧写范围不相交 |
| 12 | **证据 / 验证人·日期 / 基线 commit / 未覆盖范围** | `文件:行` 或 `命令` + 退出码；`已验证` 必须四项齐全；未覆盖写「仅 mock 适配器」等 | `已验证` 缺任一项即该行无效（`S1-04:206-217`） |

### 1.3 条目正文骨架（固定 8 节，顺序不可换）

```text
## 1 背景与来源（概念承诺原文摘录 + 归档证据，各 ≤3 行，带 路径:行）
## 2 范围（做 / 明确不做——「不做」必须给理由，`docs/README.md:121`）
## 3 验收标准（A 组功能 / B 组负例 fail-closed / C 组零回归与门）
## 4 平台边界与降级（每条带复跑命令 + 原始输出 + 三选一措辞）
## 5 依赖（含验收所需的身份/实例/会话等外部条件）
## 6 写范围
## 7 结果记录（轮末回填：逐条 A 号 → 通过/不通过/受限未验证 + 证据）
## 8 开放问题（未决 + 候选 A/B + 裁决人）
```

**载体纪律**：Dev 自证、QA 报告、探针原始输出**不回填进本条目的正文**——它们进 `docs/team/`，本条目 §7 只留一行链接 + 结论（治 A4/A6： 把 Dev 盘点、自证、轮末裁决全塞进需求文件，585 行）。

## 3. 编号与版本规范

### 3.1 编号方案（**与归档 `REQ-NNN` 不混用**）

| 对象 | 编号格式 | 说明 |
| --- | --- | --- |
| 需求条目 | `PRD-<领域码>-<NNN>`（例 `PRD-C-007`） | 领域码来自 `docs/02-产品需求/` 的领域表；同一领域内三位递增 |
| 功能点（Stage 6） | `FP-<NNN>` | 全局递增，一个功能点可服务多条需求（多对一） |
| 概念承诺 | 用**上游原生锚点**，不另编号 | `docs/01-产品概念/0X §n` / `J<n> 步骤 <k>` |
| 决策记录 | `DEC-<NNN>`（Stage 8） | 需求改方向必须引用它 |
| 缺陷 | 归档沿用 | 新体系缺陷编号规则由 Stage 7 定；本文件只要求**编号永不复用** |

**禁止**：新建 `REQ-NNN`；把归档 `REQ-NNN` 抄进新 PRD 正文当条目（只能进「来源追溯/」列）。

### 3.2 需求变更如何记录

1. **版本行只留 `vX.Y`**；一行一改进文末「变更记录」表：`日期 | 版本 | 编号 | 章节 | 一句话 | 决策人`。
2. 变更**不改标题行**、不改总表状态格之外的正文（治 A2： 单行 5813 字符）。
3. 每次改动 +0.1（`docs/README.md:90`）；冻结后改动必须引用决策记录号。
4. **追加即新条目**：新增批次不许在原条目后追加 `## 11 第二批`（v1 期反例 `REQ-019:345`、`:455`）；拆成新 `PRD-…` 并互相 `依赖`。

### 3.3 状态如何推进（谁能改 / 依据什么证据）

| 目标态 | 谁能改 | 依据（缺一不可） |
| --- | --- | --- |
| `未开工` | 需求主笔 | 上游概念已冻结 + 已登记编号 |
| `开发中` | 实现者 | 任务/产物路径已在写范围内 |
| `已实现待验` | 实现者 | 产物路径 + 自测命令 + 退出码（**自证只能到此**） |
| `已验证` | **独立 QA**（不得是自证者） | 验证人 + ISO 日期 + 命令与退出码 + 基线 commit + 未覆盖范围 |
| `平台边界` | Lead | 引用 `05-开发文档` 平台边界条目号 + 降级路径 + 复跑命令 |
| `已废弃` | Lead | 引用做出该决定的 `DEC-NNN` |

**阻塞原因**独立推进：`待决策/待批准` 必须写决策人；`待平台能力` 必须引平台边界条目号。**任何人不许在「阻塞原因」栏塞状态语义**。

## 4. 追溯矩阵规范

### 4.1 三列矩阵（唯一出处 = `docs/02-产品需求/` 内的生成物，产物 + 生成脚本思路）

```text
概念承诺 ──────────────→ 需求 ──────────────→ 页面 / 功能点
docs/01-产品概念/0X §n     PRD-<领域>-NNN      docs/03-产品设计/ 页面 或 FP-NNN
J<n> 步骤 <k>
```

### 4.2 生成方法（脚本思路，**不写脚本文件**）

1. **抽承诺**：遍历 `docs/01-产品概念/*.md` 所有 `^##`/`^###` 标题 → 生成锚点表 `{承诺ID, 文件, 节号, 标题, 行}`；旅程按 `J<n> 步骤 <k>` 行抽取。
2. **抽需求**：解析 PRD 总表的「来源追溯」列与「编号」列 → `{需求ID, 承诺ID[], 领域码}`。
3. **抽落点**：解析 `03-产品设计/` 的页面表与 `06-功能开发列表/` 的 `FP-NNN` 行 → `{落点ID, 需求ID}`。
4. **求积**：三张表按 ID 连接输出 `matrix.json` + `matrix.md`（每行 = 一个承诺 × 其需求 × 其落点）。
5. 结果只由明细算出、**不手写**（S1-04 §4 硬规则 1）。

### 4.3 校验方法（作为文档门，rc≠0 即红）

| 检查 | 判据（机检） |
| --- | --- |
| 孤儿承诺 | 每条概念承诺至少有 1 条需求，或在本矩阵显式登记「**不做** + 理由」（`docs/README.md:120`） |
| 孤儿需求 | 每条 `PRD-*` 的「来源追溯」非空且锚点可解析 |
| 孤儿落点 | 每个页面/`FP-*` 至少指向 1 条需求 |
| 死锚点 | 每个 `§n` / `J<n> 步骤 <k>` 在 `docs/01-产品概念/` 中真实存在 |
| 编号合法 | 无重复；无 `REQ-`；`PRD-` 三位连续递增 |
| 输出 | `matrix.json` 的 `orphanCommitments` / `orphanRequirements` / `orphanAnchors` 三个数组**全空** |
