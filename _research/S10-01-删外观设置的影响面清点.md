## 0. 一句话结论

**平台控制台管的是「应用品牌 + 服务页调色板」，它既不写 `/instance/settings/**`，也不管 AUP 面的 `data-tone`/`data-palette`。**
所以「删我们的外观设置」有三种量级完全不同的删法：最小的只删一个页面；彻底的会把 AUP 面外观**在编译期固定成 `.aup/app.aup` 的值**，并且必须先把主题桥里**与外观无关的 8 项修复**拆出来（否则会一并回退 `DEF-45`/白屏/页脚/对比度/点击区/退出登录等已修缺陷）。

### 1.3 它覆盖什么 / 不覆盖什么【实测】

| 命题 | 证据 | 结论 |
| --- | --- | --- |
| AUP 面的 `<html>` 属性来自平台 | `curl` 四个路由（`/?page=index`、`/posts/hello-arcblog`、`/.knowledge`、**另一个 blocklet `my-app`**）全部是 `<html lang="en" data-tone="clean" data-palette="neutral" data-mode="dark">` | 平台**运行期默认壳**，与 `app.aup` 的 `editorial/natural/light` 不同（既有 `B21`/`V09-偏差`） |
| 平台调色板**没有**进 AUP 页面 | `grep -o '1976d2\|9c27b0\|--blocklet-' /tmp/p1.html`（`/?page=index` 服务端 HTML）→ **0 命中** | 控制台的 `app:theme`（MUI 调色板）**不管** AUP 面 |
| 应用名**进了** AUP 页面 | 匿名 `--fresh` 探针：`title = "MyBlog"`（= `app:name`），而仓库声明是 `app.aup branding.title "ArcBlog"`；服务端 HTML 仍是 `<title>AFS</title>` | 平台品牌**胜出**于 app.aup 兜底（至少 `<title>` 这一项） |
| 平台**没有**写我们的设置 | `arc afs ls /blocklets/arcblog/instance/settings/arcblog` → 仍只有 `home.json` + `palette.json` + `theme.json` + `tone.json` | 控制台与 `/instance/settings/arcblog` 无写关系 |

**⇒ 关键结论**：**「完全使用控制台的外观管理」≠「站点外观仍可调」**。控制台能改的是**应用品牌（含页面标题）**与**服务页（登录/服务台/管理台）的调色板**；AUP 面的 `tone`/`palette`（editorial/clean/mono/bold × natural/warm/vivid/electric）平台**没有**对应开关，删除我方能力后它们只剩「改 DSL + 重新部署」一条路。

### 1.4 另一条可能的「控制台外观」路线：平台设置树【代码 + 未验证】

平台随包分发的参考 blocklet 里存在一条**设置树约定**（这是"把字段交给控制台管"唯一可能的形态）：

```
~/.arc/current/assets/blocklets/showcase-dsl/seed/settings/
  settings/blocklet/appearance/accent-color.json     {label,value,scope}
  settings/blocklet/appearance/compact-layout.json   {label,value,scope}
  settings/blocklet/general/{site-title,public-mode,region}.json
  settings/user/profile/{display-name,email,locale}.json
  settings-shell/app/settings.aup                    settings app { field … value=… }
```

- **没有 `settings.aup` 的树**（`settings/blocklet/**`）= 【推断】由**平台控制台**生成渲染（settings-cascade 的 README 称之为 "`configDir` 生成的 settings shell（无 tree 文件）"）；
- **有 `settings.aup` 的树** = 由 blocklet 自己的页面渲染（`my-app`：`page settings … recipe settings-shell from "/instance/settings/settings-shell/app"`；`showcase-dsl`：`page blocklet-settings … from "/instance/settings/settings-shell/app"`）。
- **本仓现状完全不同**：`seed/settings/arcblog/{tone,palette,theme}.json` 直接躺在命名空间根下、没有 `settings/blocklet/appearance/` 这一级、也没有 `settings.aup`；页面用 `auto-surface from "/instance/settings/arcblog"` 自己渲染。

【未验证】平台控制台**是否**会渲染 `seed/settings/<ns>/**` 这套树、以及它的分组名是否就是 URL 上的 `#appearance`。要判它必须**登录态**打开 `/.well-known/service/admin` 看它列出的字段（或抓 SPA 的 XHR）。
⇒ 这条路线就是下文**方案 C**，本轮不推荐先做。

### 1.5 平台自己的话：设置是「私有」的，且有一个 `public` 开关 + 服务端读原语【实测】

```bash
grep -m3 "settings-read denied" ~/.afs/daemon.log
```

```
"settings-read denied: blocklet=arcblog op=stat path=\"/instance/settings/arcblog/tone.json\" caller=anonymous-network
 — Fix: if anonymous clients must read this field, declare \"public\": true in the blocklet's
   seed/settings/<field>.json and bump its version
   (server-side reads — page render, propBind, $setting — are not affected)."
```

这条（平台原话）说明两件事，都直接影响本方案：

1. 我们为 `DEF-48` 做的**公开投影**（`node/appearance.json` + 部署步骤 2c + 桥回写）是**平台已有开关的绕行**：把字段声明成 `"public": true` 本身就是官方降级路径。**若保留外观能力**，应改用 `public`（见方案 A′）。
2. 平台还有**服务端读原语 `$setting`**（不受读门限制）——本仓从未使用。

## 4. 三个方案（按代价从低到高）

> ⚠️ **本节被 [`S10-02`](S10-02-站点主题跟随平台主题-方案.md) §3 取代**（人类口径改成"站点主题跟随平台主题"后，问题不再是"删多少"而是"完整调色板从哪来"）。保留本节是为了记录**取舍维度**与"只删界面 = 留死机械"这条结论。

| | **A · 只删界面** | **A′ · 只删界面 + 用平台 `public` 修投影** | **B · 彻底删外观能力（推荐）** | **C · 迁到平台设置树** |
| :-: | --- | --- | --- | --- |
| 做什么 | 删 §3.1 + §3.2 的编辑入口；记录与桥**原样保留** | 同 A，另把 `"public": true` 写进三个种子并升版本，删补丁 a/b/c | 删 §3.1 + §3.2 + ③ 层的"取值与应用"；桥瘦身为 `aup-fixes`（保留 §2.3 的 1–7） | 把三个字段搬到 `seed/settings/arcblog/settings/blocklet/appearance/*.json`，桥改读新路径，页面仍删 |
| AUP 面外观 | 冻结在当前记录值（`clean/natural/light`） | 同 A | **回到 `app.aup` 编译值**（预测 `editorial/natural/light`，见 §5） | 取决于控制台是否真的渲染该组 |
| 外观还能改吗 | 不能（`set` 已失效，见 §2.2） | 只能改记录/CLI | **不能**，只能改 DSL + 重新部署 | 能（在控制台里改） |
| 删掉多少"没人能用的机械" | 少 | 中 | **多**（页面/CLI/投影/部署步/测试/文档全清） | 中 |
| 风险 | 留死代码 + 一个已坏 CLI | 引入平台 `public` 的**未验证**行为（版本升级语义） | **必须**把桥的 8 项修复保住，否则回退已修缺陷 | **未验证**控制台是否渲染本仓命名空间；绑定路径变更会连带 `arc-contracts`/投影 |
| 需要探针 | 无 | 1 次（`public` 是否生效 + 升版本写法） | 无（但需 1 次匿名探针确认最终外观） | ≥1 次**登录态**探针（控制台设置树） |
| 人类检查点 | 是（口径） | 是 | 是（口径 + 若清理实例数据再加一条） | 是 |

**推荐 = B**，理由：

1. 人类裁定是"**不再管理**主题样式"，而 A/A′ 把"管理能力"留在仓库里却**没有可用入口**（§2.2 已实测 `set` 失效）——正是本仓最忌讳的"看起来还活着"的机械。
2. B 把 AUP 面外观**收敛到一个真源**（`.aup/app.aup`），与平台"应用级外观只由控制台管"的分工一致，也不再需要 `DEF-48` 的投影/回写/部署补丁三件套。
3. B 的代价可以被**精确控制**：§2.3 的 8 项修复全部有守卫，瘦身而不是删除。

**若人类要保留"能改 tone/palette"**：走 **C**，但必须先做一次登录态探针（控制台是否渲染 `seed/settings/<ns>/**` 的 `appearance` 组）；探针否证的话，退路是"B + 改 `app.aup` 走发布"。
