## 1. 主措辞（非技术语言）与"为什么现在"

> **ArcBlog 是一套你可以自己部署的博客软件。你的内容、你的读者关系、你的节点，都在你自己的 DID 之下；网络里有哪些节点在运行，写在你无法篡改的链上；而"今天值得看什么"由你自己的 agent 汇总，不由任何平台的算法决定。**

**为什么现在（三条"第一次可行"）**

| # | 变化 | 证据 |
| :-: | --- | --- |
| 1 | **链上注册表可用**：节点把 studio NFT 质押到**同一个 factory 地址**，按该地址查质押列表即**全部在运行节点**；节点可达信息（`endpoint`/`region`）写在 **NFT 的 `data.value`** 里 | 【已实现】机制 + 生产代码证据：`scripts/lib/chain.mjs:778-786` 的 `stake()` **已以 factory 为 receiver**（`:785` 为 `const to = factory.address`） |
| 2 | **agent 的读写工具面已存在**：本项目 agent 工具面 **12 个**（含 `create_draft`/`update_draft`/`publish_post`，见 `scripts/lib/agents.mjs`），跨节点**只读通道**走 `/p/` 与运行时 `/mcp` | 【已实现】（`node -e` 读 `AGENT_TOOLS` 实测 = **12**，2026-10-12；19→13 见 `PRD-AGT-13`，再随去经济/去 hub 与 `list_summaries` 调整） |
| 3 | **聚合第一次可由个人承担**：一条**领域知识即提示词**的可解释流水线（提示词版本 = 内容哈希、改提示词零代码生效）+ 多进程编排（采集 → 预筛 → 双次评分 → 写作 → 结构化 → 归组 → 成刊），是**小团队可运行**的形态 | 【规划中】（本项目尚未落该流水线；形态设计见 ``03 §J4`` 的设计要点） |

## 2. 三条设计承诺

| # | 承诺 | 含义 | 反面（明确不做） |
| :-: | --- | --- | --- |
| **P1** | **内容与读者关系归用户** | 内容存在**自己的节点**；读者关系（谁订阅、谁读过）**不被平台持有** | 不做"平台侧统一用户画像" |
| **P2** | **发现的入口在链上，不在某公司的服务器** | "有哪些节点"= **链上质押列表**；"被看见"取决于**可验证的质押事实**，不取决于某个后台的排名 | 不做中心化目录服务、不做平台侧推荐位售卖 |
| **P3** | **越简单越好** | 节点只做"写、发、被读、被汇总"；**不内置支付、结算、收益分配与访问控制** | 不做内置支付与结算 |

> **P3 的分量要说清**：这是**产品选择**，不是能力缺口——产品只由"写作 + 发现"两件事组成，交易不进入产品范围，因此不需要配套的结算凭据或收益分配规则。

## 3. 用户与收益（**优先级待人类追认**）

| 角色 | 要什么 | 得到什么 | 优先级 |
| --- | --- | --- | --- |
| **创作者（C）** | 内容与读者关系带得走；不靠平台流量 | 自有节点 + 公开 URL + 只读出口；**被汇总时署名指向自己的节点** | **入口** |
| **读者（R）** | 少花时间、看得准；不交出身份 | **被 agent 汇总过的列表**；匿名只读（无需登录、无需 Key） | **受益面** |
| **节点运营者（O）** | 一个能跑的软件 + **被发现的途径** | 部署 + 买/质押 studio NFT ⇒ **进入链上注册表即可被发现**（无需申请、无需审核） | **放大器** |
| **agent 接入方（A）** | 可读的公开面 + 明确的授权面 | `/p/llms.txt`【已实现】、`/p/rss.xml`【规划中·待生成】+ 运行时 `/mcp` + 能力档（`agent.read/write/publish`）+ 审计 | 支撑面 |

⚠️ **【已追认】（人类 2026-10-01）** 本表的排序：**创作者为入口、agent 为第二放大器、节点运营者为"新增一个可被发现的节点"的放大器**。出处 = [`concept §5-D6`](../team/concept-口径裁决-Lead.md)；决策记录 = [`docs/08-其他/01-决策记录.md`](../08-其他/01-决策记录.md) 的 `D12`。

## 5. 与相邻产品的边界

| 相邻 | 它们怎么做 | **ArcBlog 的区别** |
| --- | --- | --- |
| 普通博客平台（托管 SaaS） | 内容与读者关系在平台；发现靠平台首页/算法 | **内容与关系在自己节点**；发现源**可验证** |
| RSS 阅读器 | 订阅**你已知**的源，聚合在**客户端** | 聚合在**你的 agent**；**发现**（有哪些源值得订）来自**链上注册表**，不靠人工维护 OPML |
| 中心化 AI 聚合站 | 中心化采集 + 中心化评分/归组/成刊 | **形态可借鉴**（采集→预筛→双次评分→归组），但**聚合权归用户**：同一份公开面，**每个用户可跑自己的聚合** |
| 内容平台 + 内置支付 | 把"写"与"卖"耦合 | **不内置支付与访问控制**（P3） |

**一句话边界**：**ArcBlog 与上述产品的差别不在"能不能汇总"，而在"发现源是否可验证 + 聚合权是否归用户"。**

## 6. 不可替代性论证（展开 §0 ④）

**命题**：*"谁被看见"不由某个平台的算法决定。*

| 环节 | 中心化产品 | **ArcBlog** | 为什么中心化产品**难以复制** |
| --- | --- | --- | --- |
| **发现** | 平台后台维护目录/索引 | **链上注册表**：质押记录即目录（`listStakes(receiver=factory)`） | 中心的目录可以被"下架/排序/收费"；**链上质押事实不能** |
| **聚合** | 平台算法统一排序 | **用户自己的 agent**：同一公开面，各人可跑各人的规则 | 平台无法既给"可验证发现"又保留"排名权" |
| **可达** | 平台发 URL | 节点自己声明 `endpoint`/`region`（写在 NFT data） | 中心要复制，就得**先放弃中心化排名** |
| **内容** | 存在平台库 | 存在**节点自己的 AFS 空间** | 中心的护城河正是"内容在库里" |

**置信边界（诚实）**：① 支撑 ④ 的**枚举能力本项目尚未实现**（适配器无 `listStakes`；`grep listStakes scripts/lib/chain.mjs` = **0**；mock 链从未跑过）⇒ **【规划中】**，验证方法 = mock 链上两个节点各质押一个资产后按 factory 枚举（判据：返回条数 = 质押数，未质押者不出现）；② 跨节点**内容搬运**没有任何实现 ⇒ **【平台边界】**，且**不得**反向断言"平台不支持"（有通用原语、只是未验证）。

## 7. 明确不做什么（三层）

| 层 | 不做 | 理由 |
| --- | --- | --- |
| **产品选择** | ① 不做中心聚合入口（聚合由用户自己的 agent 承担）；② 不做内置支付·结算·收益分配·访问控制；③ 不做中心化推荐平台 | P2/P3 |
| **平台强制（【平台边界】）** | ① 不做根级自定义 HTTP 端点（被应用壳吞掉）；② 不做应用内直接发布（无运行时依赖 ⇒ 只能写意图）；③ 不承诺跨节点内容搬运（无实现） | 能力 #49/既有架构；`docs/05-开发文档/02` |
| **推迟（【规划中】/【未验证】）** | ① NFT **转让/出售**：**【规划中】已立项、路径明确**——接口 = `TransferTx{to,value,assets[],data}` 经 **`signTransferTx` → `sendTransferTx`**（证据 `node_modules/@ocap/client/lib/node.d.ts:2422/324/362/400`），**在 beta 链用 TBA 测试币验证**（`scripts/lib/chain.mjs:150-156`：beta = `https://beta.abtnetwork.io/api`，原生币为 **TBA**）；**但仍未跑过，不得写成"已经可以买卖"**；② **DID Space 记忆备份**（先本地）；③ 跨节点**订阅式同步**（`arc space sync` 远端【未验证】） | 口径 §1-5/§5 |
