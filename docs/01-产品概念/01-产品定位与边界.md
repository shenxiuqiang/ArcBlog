## 1. 这个产品是什么

### 1.1 主措辞（非技术语言，Lead 裁决 D2-A）

> **ArcBlog 是一套任何人都能自己部署的博客软件：内容归创作者，读者关系不被平台持有；多个各自部署的实例通过可验证的角色互相发现、互相分发，而不是所有人挤在同一个平台上。**

**技术副标题（D2-B，紧跟一行，不替代主措辞）**：以 DID 为身份、以 AFS 为资源层的内容节点软件。

### 1.2 两条口径必须分开写

同一句"ArcBlog 是什么"在今天有两层含义，混写就是归档期最常见的形态病（R4 §1 A1）。本文一律分开标注：

| 口径 | 表述 | 标签 | 证据 |
| --- | --- | --- | --- |
| **现状口径**（今天实际是） | 一个 DID 原生、Markdown 优先的**发布型 Blocklet**；AUP DSL + Node CLI 编写，内容在 blocklet 的 AFS 实例空间 `/instance/app/arcblog/**` | 【已实现】 | `README.md:6`、`CLAUDE.md:16`（原文："the current codebase implements the early blog-phase subset of it"）、R1 §1 |
| **目标口径**（要做成什么） | 一套 Open Source + Self Hosted + Identity Native + Content Native + Agent Native + Economy Native + Decentralized 的**内容基础设施**：Studio 为创作者节点、Hub 为发现节点、NFT+Stake 激活网络角色、支付与分成为经济基础、Agent Access 为 AI 接口 | 【规划中】 | spec §147、§153:5316、§1:29–55 |

**读者须知**：本文凡不特别标注处，描述的是**目标口径**；凡涉及"今天能做到什么"，一律落到 §4 与 `R1 §2` 的逐项状态，不用目标口径替代现状。这条纪律直接对应 R4 §1 A7（不可复现的断言是最大隐性成本）。

### 1.3 软件 ≠ 网络

必须明确：**ArcBlog Software ≠ ArcBlog Network**（spec §141:4687–4704）。任何人可以 Fork / Build / Run / Operate 这套软件；网络由运行它的节点共同组成。

由此推出两条不可让步的结论：

- **不存在"The Hub"**：官方可以运行一个 Hub，但它只是 One Hub（spec §142:4708–4728、§143:4732–4754）。本文与下游文档不得把任何单一实例写成网络的唯一入口。
- **软件不发行、不定价网络角色**：角色资产由外部 Factory 发行，ArcBlog 只负责检查资产 / 所有权 / Stake 并激活能力（spec §8.1:424–456）。

## 2. 最小单位与形态

### 2.1 基本单位 = 一个 ArcBlog Instance

ArcBlog 的基本单位不是"网站账号"，而是**一个 ArcBlog Instance**——同一份代码、同一个 Blocklet Package 的一次部署（spec §1:31–55）。

### 2.2 四种运行状态由**链上角色**决定，不由代码分支决定（实现进度见下表）

| 状态 | 激活条件 | 节点职责 | 当前可用性 |
| --- | --- | --- | --- |
| **Basic** | 默认，无需 NFT | Blog / Profile / Draft / Publish / Theme / Media（spec §7.1:275–290） | 【已实现】（R1 §2） |
| **Studio** | Studio 角色资产 + 有效 Stake | 创建/发布内容、提供公开站点与内容 API、注册到 Hub、收打赏、售付费内容（spec §7.2:294–319） | 角色链上生命周期【已实现】（真链 beta 四步各有 tx）；内容面即 Basic 链路 |
| **Hub** | Hub 角色资产 + 有效 Stake | 发现/索引/聚合/搜索/推荐/Topic/经济路由（spec §7.3:323–348） | 角色生命周期【规划中】——**当前是 mock 模拟，不是真链**；Topics 策展与推荐策略【规划中】（R1 §2） |
| **Studio + Hub** | 两个资产都有 | 同时承担生产 + 发现 + 聚合 + 经济路由（spec §7.4:352–376） | 【规划中】 |

**三件事必须分开写**（Lead 裁决 ⑤；口径以 `node/factories.json` 的**实测字段**为准，复跑命令见下）：

| 对象 | `node/factories.json` 实测字段 | 结论 |
| --- | --- | --- |
| **Studio 角色链上生命周期** | `nodes.studio.adapter="ocap"`、`simulated=false`、`chainVerified=true`、`acquireTx="ABDBD742…"`、`stakeTx="0C2D0498…"`、`revokeTx="E9971795…"`、`claimTx="631F210A…"`、`stakeAddress="zrjkV7pG…"`、`moniker="ArcBlogStudioNode #5"` | **【已实现】**（真链 beta，四步各有 tx） |
| **Hub 角色** | `nodes.hub.adapter="mock"`、`simulated=true`、`chainVerified=false`、`acquireTx="0xte32482c…"`、`stakeTx=""`、`attribution="adapter mock — SIMULATION, not chain truth"` | **【规划中】——mock 模拟，不是真链**；界面/文档均不得写成"Hub 角色链上已验证" |
| **经济（支付 / 结算）** | 全链路**声明式**：`transactionHash` 恒空、`ADAPTERS = none｜manual` | **【规划中】/【平台边界】**，**不得写"资金可用"**（`R3 §4-5`） |

```bash
# 复跑（只读）
arc afs exec /blocklets/arcblog/.actions/read --args '{"path":"/instance/app/arcblog/node/factories.json"}' --json
```

**因此不开发两套软件**：没有 `ArcBlog Studio` / `ArcBlog Hub` 两个前端，只有一套 UI 按 Capability 展开（spec §1:42–55、§58:2537–2556）。

> 注意：`Studio` / `Hub` 在本产品里**始终指节点角色**，不指两个产品、不指两个代码库。术语唯一出处 = [`04-概念与术语.md`](04-概念与术语.md)。

### 2.3 用户下载 / 运行 / 拥有的是什么

- **下载**：一个 Blocklet Package（`blocklet.yaml` + `dist/`）。
- **运行**：在 ARC 运行时上成为一个 Instance。
- **拥有**：节点身份（Node DID）与节点数据；**用户私域数据属于用户 DID 作用域**（spec §5.2:197–226、§83:3190–3209），不归节点运营者。

## 3. 给谁解决什么问题

### 3.1 三类受益人

| 受益人 | 今天的问题 | ArcBlog 给的东西 | 代价 |
| --- | --- | --- | --- |
| **创作者** | 内容与读者关系托管在别人平台上：改规则、关站、抽成时带不走 | 身份 = DID 而非平台账号；内容在 AFS，可自托管、可迁移；读者关系不归节点 | 自托管／自运维；公开面能力受平台边界限制（§7.2） |
| **节点运营者** | 想运营一个内容节点、靠发现与分发获得回报，但缺可运行的软件与可信的角色机制 | Studio 作为**链上可验证、需质押**的角色（真链四步已跑通）；Hub 角色**设计形态相同但当前是 mock**（§2.2）；发现可参与分成（spec §30–§33） | 需获取并质押角色资产；退出有等待期（spec §8.4） |
| **读者** | 想直接支持创作者，且不把身份交给平台 | DID 登录；直接付费/打赏；付费内容的门禁在**服务端**而非前端隐藏（spec §23–§24:1515–1563） | 需要 DID 会话；账号体系与主流平台不同 |

### 3.2 优先级：创作者为入口，运营者为第二价值放大器【决策待定】

**本文采用的排序（Lead 裁决 D5-B）**：以**个人创作者为入口**，**节点运营者为第二价值放大器**。

**必须标注为待追认，不得写成已定事实**，理由两条：

1. **当前只有 Basic 链路成熟**：Studio/Hub 的经济与网络能力多为 🟡 或【规划中】（R1 §2、`R1 §3` 实现账目）；把运营者当一等入口会承诺一个尚未走通的旅程。
2. **没有创作者，Hub 无内容可分发**：Hub 的价值依赖网络上已有内容供给，所以供给侧的冷启动必须由创作者承担。

⚠️ **与归档 spec 的假设不同**：spec §1/§7/§134–§137 的阶段推进（MVP-2 Studio → MVP-3 Economy → MVP-4 Agent）隐含"运营者优先"。本排序是**产品叙事层**的选择，不改变 spec 的阶段顺序。**需人类追认**（见 §8 开放问题 O1）。

### 3.3 成功标准：只给候选指标，数字留待裁决

按 Lead 裁决 D6-B，本节只写**可判定的候选指标**，具体数值一律【决策待定】：

| 受益人 | 候选成功标准（可判定） | 数值 |
| --- | --- | --- |
| 创作者 | 从"未部署"到"第一篇有公开 URL"的完成率与耗时 | 【决策待定】 |
| 节点运营者 | 从"部署"到"角色 staked 且被至少一个 Hub 收录"的完成率与耗时 | 【决策待定】 |
| 读者 | 付费后拿到 Access Grant 并读到全文的端到端成功率 | 【决策待定】 |

**不得自造指标**：上表的数值须由人类给定产品目标后填入（§8 O4）。

## 4. 用户第一次完成的一件事

### 4.1 五问③的主体 = 创作者（Lead 裁决 D4-A）

"第一次用它的人"指**创作者**（内容生产者），不是节点运营者。理由：创作者路径是今天**唯一在页面上可提交、且公开面全通**的路径（§4.2）；把未走通的路径当五问③会同时违反 G1 与 G3。

### 4.2 最短路径（现状：**可发布；署名不可信**）

```text
DID 登录
   ↓
写一篇（?page=compose 页面表单，或 CLI: node scripts/arcblog-lifecycle.mjs publish …）
   ↓
公开页出现 /posts/{slug}
   ↓
拿到 RSS（node scripts/arcblog-rss.mjs --feed-link …）
```

| 步骤 | 触点（页面 / URL / 命令 / AFS 记录） | 标签 | 证据 |
| --- | --- | --- | --- |
| 登录 | AUP 页面 `$session.authenticated` + 登录卡 | 【已实现】 | `blocklet.yaml` 权限表；R1 §6.4 |
| 写（**页面可提交**） | `?page=compose`（`exec "/.actions/write"`） | 【已实现】 | `.aup/pages/admin/compose.aup`；R1 §2 |
| **署名** | 页面写动作把 `authorDid` 落成**字面量模板** `$session.did` | **【已实现】结果错误** | 见 [`03 §1`](03-使用旅程.md) J1-3 / J1-4；`arc-contracts.md` §28.7（`$session.*` 在 `exec.content` 内不插值） |
| 发布落库 | `/instance/app/arcblog/posts/<slug>.json`（guest 可读） | 【已实现】 | 见 [`03 §1`](03-使用旅程.md) J1-4；`blocklet.yaml` 的 `replicated`/`networkRead` |
| 公开访问 | 绑定路由 `/posts/{slug}` → `reader` 页（`propBind` 取记录） | 【已实现】 | `blocklet.yaml` `sites[].bindings`；R1 §6.2 |
| 分发 | `scripts/arcblog-rss.mjs` 生成 RSS | 【已实现】 | R1 §2「SEO/Feeds」行 |

**准确口径（三句话，不得互相覆盖）**：① **页面可以提交**、**公开面可以访问**（上表【已实现】）；② **署名不可信**——页面路径产出的 `authorDid` 是字面量（标为「【已实现】结果错误」）；③ 今天**唯一署名可信**的路径是 CLI `publish`，它显式写 `authorDid`（`scripts/arcblog-lifecycle.mjs`）。所以本节的标题是"**可发布；署名不可信**"，而不是"全部【已实现】"。

### 4.3 第二条旅程：节点运营者（不占五问③）

```text
部署一个 Instance  →  发布至少一篇  →  获取并质押 Studio 角色（?page=factory）  →  注册到一个 Hub（arcblog-network.mjs hub register）
```

这条路径的每一步都超过一次交互，且**上链动作必然是"意图队列 + 本机 worker"**（私钥不进浏览器，见 §7.2 B9）。它是 Stage 1 的第二条旅程，**已在 [`03 §8`](03-使用旅程.md)（J8 新建节点上线）逐步展开**，不占五问③。

## 5. 与相邻产品的关系（依据 R2 §3，v0.2 定稿）

> 本节结论**全部来自调研 R2** [`S1-02-用户视角与对标.md`](../08-其他/调研/S1-02-用户视角与对标.md) §3（8 个产品 × 借什么/不借什么），主笔不再自行检索。R2 自述的取证限制见该文 §6.4：Substack 帮助中心 403，Hashnode/Mirror/Medium 未抓一手页面（相关描述标"公开产品形态"）；Ghost / WordPress / Paragraph 有一手页面。

### 5.1 八个对标产品：借什么、不借什么（R2 §3）

| 产品 | 它解决了什么 | 我们**借**的模式 | 我们**不借**的 |
| --- | --- | --- | --- |
| Medium | 编辑即写作 + 站内推荐流 + 会员制计量付费墙 | 写作界面只留写作（编辑器应是全屏文档，不是 12 字段表单） | 平台级付费墙：读者关系记在平台账上，与"内容属于创作者"冲突（spec §2） |
| Substack | 开号即订阅页；付费订阅直给订阅者名单与收款 | 「订阅即付费边界」+ 收益页讲清"谁付了、何时到账" | 邮件列表为核心的架构：读者身份绑邮箱，与 DID 原生身份重复 |
| Ghost | 自托管与托管同源；成员/付费走 Stripe Connect；自定义域名是一等公民 | 自托管也能有托管级 IA 与视觉；外部依赖给公开可预期的接入点 | "必须连第三方支付商才算能用"：我们把 `manual` 当诚实降级，支付是可替换接缝（spec §44） |
| WordPress | 媒体库网格 + 附件详情页可查"谁在用它"；分类/标签两套独立面 | 媒体库要有引用视图与详情页（spec:1007–1009） | 插件式补丁生态：插件改后台数据模型会破坏 AFS 真源与签名/门禁链 |
| Hashnode | 开发者向：登录即开站、自带域名与导出叙事 | 「开站 3 步内完成」的冷启动节奏（对应 J1 步骤 1） | 以 GitHub 为身份源：身份必须是 DID（spec §107:3905–3919） |
| Paragraph（继承 Mirror 的 Web3 写作位） | 同一付费墙同时接法币与加密；加密路径不需要邮箱；持有即会员 | 同一付费墙支持**法币 + 加密双通道**——**这是我们今天最大的缺口**（§6.5） | "持有代币 = 解锁"的整体代币化（spec §139:4648–4656 明确不做 Token/DAO） |
| 个人站点 + 自有域名（Astro/Hugo + Vercel/Netlify） | 内容即文件：可迁移、可 diff、可离线；代价是没有后台与付费 | 「导出/迁移是一等公民」的叙事与验收项（spec:1286） | "只有工程师能维护"：spec:994 要求运营者像编辑文档一样维护 |
| AT Protocol / Bluesky（身份可携带类比） | 身份是域名（handle），换服务不改身份 | 「身份可携带 ⇒ 换节点不丢读者关系」用于解释 DID 的价值 | 域名即身份的绑定：我们的身份是 DID，域名只是 endpoint（spec §109:3946–3957） |

R2 把它归结为 **借 7 个模式**（全屏文档式编辑器 / 订阅即付费边界与收益透明 / 媒体库引用详情 / 开站三步 / 双通道支付 / 导出迁移优先 / 身份可携带）与 **明确不借 5 个**（平台级付费墙 / 邮件列表为核心 / 插件生态 / 代币化会员 / 域名即身份），并强调**只借交互模式与承诺口径，不借功能清单**（R2 §3 末段）。

### 5.2 与"发现者分成"先例的关系（保留诚实标注）

主叙事（§6.1）涉及"发现者获得回报"，它在**领域外**有先例：[Nina Protocol](https://musically.com/2025/10/13/nina-to-share-revenues-with-fans-who-help-get-music-discovered/) 已上线"为发现音乐付费给粉丝/策展人"的分成系统（[Record of the Day](https://www.recordoftheday.com/news-and-press/nina-protocol-launches-revenue-share-system-that-pays-fans-for-music-discovery)）。

**必须保留的标注**：该模式**借自音乐领域**；在**内容阅读**场景下，R2 §3 的 8 个对标产品**均未提供**"第三方按可验证归属分成"这一层。所以它既是本产品叙事的立足点，也是**未被任何对标产品验证过的假设**。

### 5.3 结论

1. **已被商品化的能力**（不得当卖点）：自托管发布、身份可携带、RSS 分发、去中心化发布协议；写作体验、媒体库、开站速度、导出优先也都有成熟范式可借（§5.1）。
2. **对标里没有的那一层**：让**第三方发现节点**在**内容销售**中按**可验证归属**分成，且该角色需**质押**才有资格参与——8 个产品**据现有取证**无一涉及。
3. **该全称否定的取证限定（不得省略）**：R2 §3 自述 8 项中 **4–5 项非一手核验**（Substack 帮助中心 403；Hashnode / Mirror / Medium 未抓一手页面；Ghost / WordPress / Paragraph 有一手页面，见 R2 §6.4）。因此本条应读作"**据 R2 §3 现有取证未发现**"，而不是"已证明不存在"；补齐一手核验 = **Stage 2 前置项**（见 §8 O3）。
4. **但这一层今天的产品证据为零**：R2 §2 的 J2/J3 显示付费闭环与 Hub 收益面在浏览器里都不存在（唯一出处见 §6.5）。**不可替代性是设计命题，不是已兑现的能力。**

## 6. 不可替代性（Lead 裁决 D3：B 为主叙事）

### 6.1 主叙事 B：发现是一个可验证归属、可分成、按角色参与的开放网络

> **ArcBlog 的差异不在"内容归创作者"（那已被部分解决），而在：谁来发现、凭什么分钱、按什么资格参与——这三件事在 ArcBlog 里是一个开放的、链上可验证的角色市场。**

- **可验证归属**：Hub 的收益依据是"为该经济活动提供了可验证的发现/推荐/交易入口服务"，用签名的 Discovery Context 证明，而不是靠不可靠的 HTTP Referer（spec §30:1706–1738、§31:1740–1774、§32:1776–1810、§33:1812–1836）。
- **未验证则归创作者**：归属验证失败时不产生 Hub 份额，折回创作者（R1 §2「归因/分成」行；`config/trusted-hubs/` + `economy/attributions/`）。
- **按角色参与**：能参与的是持有并质押了 Hub 角色的节点（spec §7.3、§8.3），不是任意第三方。

**证据状态**：归属与分成的**机制**【已实现】（Ed25519 Discovery Context + 可信 Hub 公钥 + 版本化分成策略，spec §29:1673–1702）；**跨节点分发**为**【规划中】——按 §7.2 B8 的写法：平台有通用搬运原语（`arc space sync`），我们尚未实现跨节点同步**（**不得**写成"平台不支持跨节点同步"，那是 `R3 §4-8` 明令禁止的反向断言）；**闭环与 Hub 收益面**【规划中】（§6.5）。据 R2 §3 现有取证（8 项中 4–5 项非一手），无一提供这一层（§5.3）。

### 6.2 前提 A：身份与内容归属（不单独构成不可替代性）

创作者身份 = DID，内容在 AFS 可自托管/迁移（spec §107:3890–3919、§5.2、§83）。

**为什么它只是前提**：R2 §3 的 Ghost 行（自托管 + 会员制，Stripe Connect）与 AT Protocol 行（身份可携带）已经覆盖了"自己拥有网站"与"身份可携带"（§5.1）。因此**不得**把 A 单独写成卖点——这正是归档期最容易犯的"把前提当结论"。

### 6.3 第二楔子 C：Agent 是一等公民

ArcBlog 复用 ARC 运行时的 Agent Access（`/mcp`、AFS RPC、`llms.txt`），只声明能力与审计，不自造一套 Agent 协议（spec §59:2560–2562、§129:4382–4394）；能力分级 `agent.read/write/publish/economy/admin`，默认只读，高风险工具永不暴露（spec §61:2584–2612、§130:4404–4438）。

**定位**：这是**第二个楔子**，不是主叙事。它的价值在"内容网络天生可被机器消费"，但单独不足以让人换产品。

### 6.4 反例与证伪点（写出来，别藏）

| # | 反例（"用户为什么不直接用 X"） | 本产品的回应 | 依据 / 回应是否成立 |
| :-: | --- | --- | --- |
| C1 | 我用 Ghost 自托管，站点和订阅都是我的 | 你拥有**站点与订阅关系**，但不拥有**网络**：没有第三方节点靠发现你的内容获得收益 | R2 §3 Ghost 行；回应未被任何对标产品验证（§5.2） |
| C2 | 我在 Bluesky/Nostr 上，身份已经是可迁移的 | 协议解决了身份搬运，没有解决"发现的经济归属" | R2 §3 AT Protocol 行；同上 |
| C3 | Paragraph/Mirror 已经能用法币+加密双通道付费 | 双通道我们**要借**（R2 §3），它不构成差异；差异在"谁因发现而分到钱" | R2 §3 Paragraph 行 |
| C4 | Nina 已经在给发现者分成了 | Nina 在**音乐**领域；本产品把同一模式放进**文字内容的销售**，并要求发现者是**质押过的节点** | §5.2；**未被内容阅读场景验证** |
| C5 | 我只要 RSS + 一个阅读器就够了 | 对纯读者成立；RSS 不给付费门禁、访问授权与创作者结算 | R2 §3 个人站点行；**部分成立** |
| C6 | **你的付费墙现在根本付不了钱** | **属实**。R2 §2 J2 步骤 3–5：墙内无购买动作、商店页无收银台、全文只能 CLI 取 | **反例成立**——见 §6.5，不得辩解 |

### 6.5 诚实边界：不可替代性今天**还不是**可用能力

主叙事 B 依赖"发现的归属可验证、可分成"，而这条链路在浏览器里目前**没有路径**。本节**只给结论**，逐环节证据不在此复制（唯一出处原则）：

| 断点 | 一行结论 | 唯一出处 | 状态 |
| --- | --- | --- | --- |
| **付费闭环**（看见价格 → 购买 → 支付 → 解锁 → 凭据） | 浏览器里**无路径**（页面无购买动作、商店无收银台、全文只能 CLI 取） | [`03 §2.1`](03-使用旅程.md) | 【规划中】+【平台边界】 |
| **Hub 收益面** | Hub 视角"我分到多少"**没有落点** | [`03 §4`](03-使用旅程.md) J3-5 | 【规划中】 |
| **跨节点分发** | **我们尚未实现**（平台有搬运原语 `arc space sync`；**禁止**反向断言"平台不支持"，见 §7.2 B8） | 本文 §7.2 B8 | 【规划中】 |

**结论（不许含糊）**：ArcBlog 的不可替代性目前是一个**有机制、无闭环**的设计命题——机制层【已实现】（§6.1），闭环层【规划中】（上表）。Stage 2 的需求优先级必须从这三条断点出发，而不是从 §6.1 的愿景出发。
