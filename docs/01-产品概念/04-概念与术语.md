## 0. 用法与登记规则

1. **一个术语一个出处**：同一概念只在本文件（或本文件明确指向的 Stage 文件）定义一次；其它文档**只链接**，不复制定义（总纲 §2 原则 2；R4 §1 A1）。
2. **先登记后使用**：新增术语先在总纲 `docs/README.md` §6 与本文登记，再进正文（总纲 §6）。
3. **三类条目，写法不同**：

| 类别 | 写法 | 例 |
| --- | --- | --- |
| **本目录定义** | 给一句定义 + 出处 | Instance、Discovery Context |
| **跨阶段引用** | **只登记名称 + 指向唯一出处**，本文件不定义 | 意图队列（→ `03-产品设计/`）、平台边界汇总（→ `05-开发文档/`）、质量门（→ `07-团队与开发规范/`） |
| **归档术语（不再使用）** | 标注"已废弃"+ 替代词 | 见 §9 |

4. **命名冲突的处理**：调研文件用 `R1–R7` 指**角色**，而调研编号 `R1–R4` 指**调研文件**。本体系一律用 §1 的角色代号，**禁止**在正文用 `R1–R7` 指角色。

## 2. 核心对象

| 术语 | 一句定义 | 唯一出处 |
| --- | --- | --- |

| **Node DID** | 节点对外身份；作者身份同样是 DID，**不用 `username` 作最终身份**（username 只是 UI alias） | spec §107、§109；`01 §2.3` |

## 3. 角色与能力

| 术语 | 一句定义 | 唯一出处 |
| --- | --- | --- |
| **角色资产 / 角色 NFT** | 表示"某 Instance 获得某种网络角色的链上资格"，**不是会员卡**；ArcBlog 只检查资产/所有权/Stake 并激活能力 | spec §8；`01 §1.3` |
| **NFT Factory** | 发行角色资产的链上工厂；**地址外部化，ArcBlog 只消费不实现**，发行与定价属 Factory owner | spec §8.1、§9；`01 §7.1` P1 |
| **Stake（质押）** | 运营者以资产为节点持续运营背书；质押时把节点展示信息写入 NFT data（质押中不可修改） | spec §8.3 |
| **Revoke & Claim（解除质押与取回）** | 两阶段退出：revoke → 等待期（能力立即降级）→ claim（资产回钱包，可重新质押） | spec §8.4 |
| **角色生命周期五态** | 名称与顺序**固定为** `none → acquired → staked → revoking → claimable`（→ acquired）；只有 `staked` 才可能激活能力 | 名称表 = 本节；**语义与转换规则 = `docs/02-产品需求/`（未写）**；底层单一真源 `scripts/lib/roles.mjs`、spec §8.5 |
| **RoleStatus** | 角色可查询状态：`assetOwned` / `stakeActive` / `stakeState` / `active` / `assetId` / `stakeId` / 时间戳 | spec §8.5、§10 |
| **Role Engine** | Identity → Asset Ownership → Stake Status → Role → Capability 的统一判定链 | spec §10 |
| **Capability / Capability Engine** | 把 Role 映射为能力（`studio.publish`、`hub.index`…）；**代码里不写 `if (isHub)`** | spec §11 |
| **fail-closed** | 角色未验证 ⇒ 不授予任何能力（"未验证即拒绝"是本体系的默认姿态） | `scripts/lib/roles.mjs`；`R3 §3 P4` |

> **为什么把五态写在这里**：归档期同一控制台出现过三套意图状态叫法（R4 §1 A8），代价是 P1 阻断放行。本体系的做法是**词表集中、语义分散到需求**：名称只在本文固定，规则只写在 `02-产品需求/`。

## 4. 经济

| 术语 | 一句定义 | 唯一出处 |
| --- | --- | --- |
| **Product（商品抽象）** | "可销售的东西"的统一抽象，是内容与价格之间的隔离层：文章只挂 `productId`，改价不动文章 | spec §39、§41、§45 |
| **Order（订单）** | 经济系统的唯一入口事实；状态 `pending/paid/failed/refunded`；**今天默认整链路零链调用**（`transactionHash` 恒空，支付为声明式） | spec §42；`01 §2.2` |
| **Payment ≠ Settlement** | 支付与结算是两个独立步骤，互不隐含 | spec §89 |
| **Settlement（结算）** | 按**当时**的 settlement version 把订单金额分账 | spec §43 |
| **Revenue Split（版本化分成）** | 分成规则版本化（初始建议 creator/hub/protocol = 0.80/0.15/0.05）；**历史订单永远按当时版本结算** | spec §29 |
| **Economic Ledger（账本）** | append-only，确定性 id `<orderId>:<type>`；只增不删 | spec §91、§92 |
| **Access Grant** | 付费阅读成功后产生的阅读授权 `{contentId, readerDid, orderId, grantedAt, expiresAt}`；`expiresAt: null` = 永久 | spec §37 |
| **Paid Reading（付费阅读）** | 支付产生 Access Grant 解锁全文；正文存 `paid/`（admin-only），公开记录只留 `previewOnly`——**安全靠服务端，不靠前端隐藏** | spec §23、§24、§86 |
| **Tip（打赏）** | `kind: tip` 的支付；**不产生访问权**（与 Paid Reading 的区别） | spec §35、§36 |
| **Hub Share** | Hub 收益的**唯一依据**：为该经济活动提供了**可验证的**发现/推荐/交易入口服务 | spec §30 |
| **Attribution（归属）** | 对 Hub 贡献的验证；**未验证则归属折回创作者** | spec §30–§33；禁写"链上已验证/已结算"属 `R3 §4-5` 家族 |
| **Discovery Context** | Hub 签发的发现凭证 `{hubDid, studioDid, contentId, issuedAt, expiresAt, signature}`，替代不可靠的 HTTP Referer | spec §31、§32 |
| **Subscription（订阅）** | 手动续期（无自动扣款）；续期 = 新订单产生新 Grant | spec §38 |

## 8. 五类事实标签（全体系通用）

| 标签 | 含义 | 何时使用 |
| --- | --- | --- |
| **【已实现】** | 有代码 / 记录 / 命令证据 | 断言"今天能做到"时必须给 `文件:行`、命令输出或 AFS 记录 |
| **【规划中】** | spec 有定义、代码无落点或已回退 | 必须同时给目标 Stage 或需求编号 |
| **【平台边界】** | 平台不支持或已降级 | 必须给 `arc` 实测出处 + 降级路径（归档证据 `_docs/arc-contracts.md`） |
| **【决策待定】** | 候选方案未拍板 | 必须写候选 A/B 与裁决人 |
| **【未验证】** | **事实还不知道**——需要一次探针/实测才能钉死 | 必须写"**未验证什么 + 为什么现在验不了 + 验证方法/判定式**"；**不得**据此下结论 |

**分工（与【决策待定】的区别）**：【未验证】= 事实还不知道（要实测）；【决策待定】= 事实已清楚但选择未拍板（要人裁决）。**标签的唯一出处 = 总纲 [`docs/README.md`](../README.md) §4**（本篇只作术语层登记）。

**禁止写法**："应该能""大概支持""更好""更完善"（总纲 §4）。反向断言同样受管：**"平台不支持 X"也必须举证**（R4 §1 A7、`R3 §4` 禁止清单第 8 条）。
