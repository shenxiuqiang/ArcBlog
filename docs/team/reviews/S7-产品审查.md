## 3. 我认为对的 3 条

1. **`02 §8` 的受控修订六步是"可照着走"的样板**：每一步都附**"若不做的后果（真实发生过）"**（非属主改 ⇒ 属主只能挂起上报；无留痕 ⇒ 记录与实况对不上；不重跑门 ⇒ 静默破坏；旧 hash 不标取代 ⇒ 记录看似自相矛盾），并给 **7 次实例**（含最完整的 `S3 §1.1` 七栏）+ 两条硬约束（非属主留痕 / `P15` 扫全库且"相容的不必改"的反面例）。**"给判据 + 给事故 + 给范例"三件齐**，这是本项目纪律文档里最"能照做"的一节。
2. **`03 §1` 把"两道门"的独立性写成了判据而不是口号**：明确 "`npm test` 不调用 `arc dsl validate` ⇒ 必须都跑"、判据用**解析出的 `issues: []` / `fast tier passed` 而非退出码**（因为平台 `arc` 命令出错时 `$?` 可能为 0）、文件数与耗时**从运行输出取、不写死**；`§4` 还给出"表体行数 = 实测计数"的可复跑一致性检查。**这三条正好是本项目历史上最贵的三次事故的固化**。
3. **`04 §2` 敢把"未提交"写成正式条文**：不列"提交记录清单"（因为本会话确实没有），而是写"何时可提交 + 提交前必须核什么"，并明写"基线 `4597ba2` 只是未变动的 HEAD，**不要读成已提交**"；由此推出"**回滚不是安全网**"+`BUG-079`+"恢复靠文件不靠记忆"。**把不利事实写成规则而不是回避**，且与 `06 §3` 的"本会话违反过？"列互相印证。
