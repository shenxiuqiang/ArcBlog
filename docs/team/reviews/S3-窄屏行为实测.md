## 0. 一句话答案

> **「窄屏折叠为顶部导航」今天没有实现，但平台已经把 CSS 写好了**——`@media (max-width:640px)` 对 `.aup-view[data-variant="nav-sidebar"]` 给出 `flex-direction: column` + `width:100%` + `max-height:40vh`（正是"顶部导航"）。ArcBlog 的侧栏是**无 variant 的裸 `view`**，所以这条规则永不命中。Stage 3 只需（a）决定采用哪种降级，（b）验证 DSL 是否允许给 `view` 加 `variant=`。

## 1. 探针能力与限制（为什么必须自己驱动 CDP）

`scripts/arcblog-browser-probe.mjs`（只读源码）**认识的全部 flag**：

```text
flag('cookie-file') flag('port') flag('profile') flag('screenshot') flag('settle') flag('timeout') has('screenshot')
```

⇒ **没有** `--viewport` / `--width` / `--height`，也**不调用** `Emulation.setDeviceMetricsOverride`；其 `probeJs` 只回传：`title / url / sessionInitFailed / aupNodes / firstNode{id,w,h} / gateText / text(前 400 字) / documentCookies` —— **没有** `innerWidth`、`scrollWidth`、侧栏元素、`--aup-content-max`。

⇒ 探针只能给"页面挂载 + 登录门"的基线，**做不到本任务要求的四视口量测**。按纪律我**没有改脚本**，改为连接同一 headless Chrome 的 CDP 端点（`127.0.0.1:9334`）自行量测；脚本经 stdin 传入、未落盘。

## 2. 关键前置事实：**控制台侧栏在无会话时根本不存在**

无登录会话时，两个控制台页面只渲染登录门（探针原始输出）：

```json
// node scripts/arcblog-browser-probe.mjs 'http://arcblog.localhost:4939/?page=posts' --json
{ "url": "…/?page=posts", "aupNodes": 11,
  "firstNode": { "id": "wrapper-view-1", "w": 756, "h": 469 },
  "gateText": "Sign in with", "sessionInitFailed": false,
  "text": "ArcBlog\nYour studio\nSign in with DID Wallet to manage drafts, published stories and uploaded media.…" }

// …?page=compose-edit → 同样 aupNodes=11、gateText="Sign in with"、text="Edit post…"
```

对照公开首页 `/`：`aupNodes: 39`、`gateText: null`、含 "Latest published" 与 About/Store/Author/Reading list/RSS。

CDP 量测的旁证：在全部 4 个视口、两个控制台页面上，**控制台导航标签命中数 = 0**（`presentLabels: []`，检测词表 `Dashboard/Posts/Compose/Appearance/Operations/Factory/Log out`），且**没有任何左侧栏候选元素**。

源码解释（只读）：侧栏在认证分支内、且**无 variant** ——

```aup
// .aup/pages/admin/posts.aup:65-66
row gap=lg cross=stretch style={width: "100vw", …, height: "calc(100vh - 48px)", …} visible=$session.authenticated {
  view size={width: "clamp(200px, 15vw, 280px)", flexShrink: 0, height: "100%"} style={…, overflowY: auto, …} visible=$session.authenticated {
```

⇒ **带侧栏的控制台页布局无法在无会话下实测**。因此本报告把它拆成两部分：**(A) 平台/CSS 层（可实测，见 §4）** + **(B) 侧栏宽度将解析成多少（用同一浏览器在同一视口实测 clamp，见 §3）**；真正的"侧栏与内容并排时的换行"标记为【未验证】（§6）。

## 3. 逐视口实测结果

### 3.1 公开首页 `/`（完整可测）

| 视口 | innerWidth | docScrollWidth / clientWidth | 横向溢出 | 节点数 | 内容容器宽 @x | 页高 | footer 导航 |
| :-: | :-: | :-: | :-: | :-: | :-: | :-: | :-: |
| 1280×800 | 1280 | 1280 / 1280 | **否** | 39 | `index-view-1` **1200** @40 | 1367 | About/Store/Author/Reading list/RSS ✅ |
| 1024×768 | 1024 | 1024 / 1024 | **否** | 39 | `index-view-1` **1024** @0 | 1290 | 同上 ✅ |
| 768×1024 | 768 | 768 / 768 | **否** | 39 | `index-view-1` **768** @0 | 1194 | 同上 ✅ |
| 375×812 | 375 | 375 / 375 | **否** | 39 | `index-view-1` **375** @0 | 1510 | 同上 ✅ |

- `--aup-content-max` 在 4 个视口实测均 = **`1200px`**；1280 视口下内容恰好 **1200px + 左右各 40px**，**未裁切**（`clipped: []`）；
- 1024/768/375 下内容容器 = 视口宽（上限不生效，也不溢出）；
- **无横向滚动**、**无被裁元素**——§7 第二半句「内容区不横向滚动」在公开面上**成立**。

### 3.2 控制台登录门（`?page=posts` / `?page=compose-edit`）

| 视口 | innerWidth | 横向溢出 | clipped | 侧栏候选 | 控制台标签 | header 高 | 结论 |
| :-: | :-: | :-: | :-: | :-: | :-: | :-: | --- |
| 1280×800 | 1280 | 否 | 0 | 无 | 0 | `site-header` 48px | 不折叠（无侧栏）、无横向滚动 |
| 1024×768 | 1024 | 否 | 0 | 无 | 0 | 48px | 同上 |
| 768×1024 | 768 | 否 | 0 | 无 | 0 | **56px** | 同上 |
| 375×812 | 375 | 否 | 0 | 无 | 0 | **56px** | 同上 |

- 登录门卡在 375px 下**不溢出、不裁切**（`aupNodeCount=11`、`clipped=[]`）⇒ 门本身是响应式的；
- `site-header` 高度 **48px → 56px（≤768）** ⇒ 平台/wrapper 层**确实存在一个响应式变化**（不是"全站零响应"）；
- 注意：此处的「不折叠」**不构成对 §7 的证伪**——因为**侧栏压根没渲染**；他只是说明门页可用。

### 3.3 侧栏宽度会解析成多少（同浏览器 clamp 实测）

侧栏宽度声明是 `clamp(200px, 15vw, 280px)`。在**每个视口的真实浏览器**里测量同一表达式的解析值：

| 视口 | `15vw` | `clamp(200px, 15vw, 280px)` 实测 | 含义 |
| :-: | :-: | :-: | --- |
| 1280 | 192 | **200px** | 取 200 下限（15vw<200） |
| 1024 | 154 | **200px** | 取 200 下限 |
| 768 | 115 | **200px** | 取 200 下限 |
| 375 | 56 | **200px** | 取 200 下限 ⇒ **占视口 53%** |

⇒ 侧栏宽度在四个视口**恒为 200px**；`flexShrink: 0` ⇒ 它**不会收缩**。这就是"没有折叠"的量化形态。

## 4. 关键发现：**平台其实内置了"侧栏 → 顶部导航"断点**

在控制台页面（无会话、375×812）枚举**运行时 document 里的全部 `@media` 规则**（56 条），其中与侧栏相关的原文：

```css
/* @media (max-width: 640px) */
.aup-view[data-layout="row"]:has(> [data-variant="nav-sidebar"]) { flex-direction: column; }
.aup-view[data-variant="nav-sidebar"],
.aup-view[data-layout="row"] > .aup-view[data-variant="nav-sidebar"] {
  flex: 0 0 auto; width: 100%; min-width: 0px; max-width: none;
  max-height: 40vh; border-right: none; border-bottom: 1px solid var(--color-border);
}

/* @media (max-width: 768px) */
.aup-view[data-mode="shell"] > [data-role="body"] > [data-role="sidebar"] { display: none; }

/* @media (max-width: 900px) */
.aup-view[data-variant="settings-sidebar"], .aup-view[data-variant="scaffold-sidebar"] { position: static; width: 100%; max-width: none; }
```

**这段 CSS 就是归档 §7 描述的行为**：行容器 `flex-direction: column` + 侧栏 `width:100%` + 底部边框 = **侧栏变成内容之上的横向条**。

而 ArcBlog 的现状：

```bash
$ grep -rn '@media' .aup/ | wc -l                    → 0        # .web/ 有 56（主题/组件，与控制台外壳无关）
$ grep -nE 'breakpoint|matchMedia|innerWidth|@media|max-width|min-width' scripts/console-nav.mjs  → 0 命中
$ grep -rn 'nav-sidebar' .aup/ scripts/              → 0 命中
$ grep -rln 'clamp(200px, 15vw, 280px)' .aup/pages/ | wc -l → 21   # 21 个控制台页各有一份侧栏，全部无 variant
```

即：**平台提供了能力，ArcBlog 没有 opt-in**。另有一条重要的可行性证据：`.aup/wrapper.aup:41` 用了 `view mode=shell`，编译产物 `.aup/wrapper.json:14` 为 `"mode": "shell"`（运行时即 `data-mode="shell"`）⇒ **`view` 确实接受会编译成 `data-*` 的语义 prop**；据此 `variant="nav-sidebar"` 很可能同样可用，但**我未在实例上验证过**（见 §6）。

## 5. 归档 §7 声明判定

| §7 的子句 | 判定 | 依据 |
| --- | --- | --- |
| 「窄屏时侧边栏**折叠为顶部导航**」 | **【不成立】（当前实现）** | 实测 clamp：侧栏宽在 375px 仍 **200px**（占 53%）；`.aup/` 0 条 `@media`、生成器 0 断点、侧栏无 `variant` ⇒ 平台那条 `≤640px → column` 规则**永不命中**。**平台能力存在，ArcBlog 未启用** |
| 「内容区**不横向滚动**」 | **【成立】（实测）** | 公开首页 4 视口 `scrollWidth == clientWidth`（1280/1024/768/375），`clipped: []`；登录门页同样 4/4 无溢出 |
| 「桌面优先」 | **【成立】** | 1280/1024 下 1200px（`--aup-content-max`）被正确尊重（1280→内容 1200 + 40px 边距），未裁切 |

> **"侧栏折叠"这一条不是平台边界（【平台边界】），而是"未实现的设计决策"** —— 这个区分对 Stage 3 很重要：前者意味着必须降级，后者意味着可以低成本达成。

## 6. 【已实现】（实测证据）vs【未验证】（探针/纪律做不到）

**【已实现】**
1. 公开首页在 1280/1024/768/375 **无横向滚动、无被裁元素**（`docScrollWidth==clientWidth`，`clipped: []`，4/4）。
2. `--aup-content-max` = **1200px**；1280 视口下内容恰好 1200px（x=40）⇒ 上限生效且未裁切。
3. 登录门页 4/4 视口不溢出、不裁切（`aupNodes=11`）。
4. `site-header` 48px → **56px（≤768）** ⇒ 平台层存在响应式变化。
5. `.aup/` 内 `@media` = **0**；`console-nav.mjs` 断点逻辑 = **0**；侧栏 `view` = **无 variant**；21 个控制台页共用同一份无 variant 侧栏。
6. 侧栏宽度声明 `clamp(200px,15vw,280px)` 在 4 个视口**实测均为 200px**（同浏览器解析）。
7. 平台断点样式真实存在（`≤640` nav-sidebar → `column/100%/40vh`；`≤768` shell sidebar → `display:none`）。
8. `view mode=shell` → `.aup/wrapper.json "mode": "shell"` ⇒ `view` 接受 `data-*` 语义 prop（**实测**）。

**【未验证】**
1. **认证态下侧栏与内容的实际并排/换行几何**（375 下内容可用宽、是否真出现横向滚动）—— 需 DID 登录会话；本任务明令不取 cookie/不登录。→ 验证方法：登录后对 `?page=posts` 重复 §3 量测。
2. **`variant="nav-sidebar"` 是否是合法的 `view` prop** —— `arc dsl schema --json` **不含 prop 元数据**（只有 63 个 primitive 名 + 一行 hover；全文 `"variant"` 出现 **0** 次），aup-dsl skill 也无 `nav-sidebar` 记录。→ 探针：在**一个**控制台页的侧栏 `view` 上加 `variant="nav-sidebar"` → `arc dsl validate --json` → 重启+复挂 → 375 下断言运行时 DOM 出现 `data-variant="nav-sidebar"` 且该行 `flex-direction: column`。
3. **真实触屏手势 / 触摸目标尺寸**（`Emulation` 只改视口，不模拟触摸）。
4. **CJK 长文案在 375 下的换行与截断**（本次只量几何，未做文案级断言）。
5. **`?page=compose-edit` 在认证态的编辑器窄屏行为**（表单 `input` 是否会横向挤压）—— 同 1。

## 7. 三条设计建议（给 Stage 3）

1. **把「窄屏折叠」写成待落地的设计决策，不要写成已有能力。** 在 `03-产品设计/` 里给出：目标形态（<640px = 内容之上的横向导航条；640–1200 = 左侧栏）、以及**可判定验收**——例如「375×812 下侧栏元素 `width ≈ 视口宽` 且 `y` 在 header 之下且位于内容之上；`documentElement.scrollWidth == innerWidth`」。当天可用的**回归判据**：375 下 `documentElement.scrollWidth == 375`（今天在公开面/门页已为真，实施折叠后仍须为真）。
2. **首选实现路径 = 让侧栏 opt-in 平台的 `variant="nav-sidebar"`（一行/一处改动，覆盖 21 页）**：侧栏由 `scripts/console-nav.mjs` → `scripts/arcblog-console-nav.mjs` 统一生成进 21 个控制台页，因此**只需改生成器模板一次**；平台在 `≤640px` 自动给出 `column + width:100% + max-height:40vh`。**前置探针（必须先跑）**：在 1 页上加该 prop，`arc dsl validate --json` → 重启+复挂 → 375 断言 `data-variant="nav-sidebar"` 存在且 `flex-direction: column`；**若 DSL 不接受该 prop**，退路二选一：(a) `mode=shell`（平台在 `≤768` 直接 `display:none` 隐藏侧栏 + 另做顶部「菜单」入口，语义是"隐藏"不是"顶部导航"）；(b) 自写 `@media (max-width:640px)` 到页面 `style`（与"`.aup/` 内 0 条 @media"的现状相反，需先确认 AUP 是否允许 `@media` 通过 safe-style 白名单——**同为【未验证】**）。
3. **分档要给"内容可用宽"的预算，并在 375 解决导航可达性**：1280 时内容已吃满 1200 上限，768 时若保留 200px 侧栏则内容仅剩约 **568px**（768−200−边距）——**这恰是"640–1200 该不该也折叠"的判据来源**。375 折叠为顶部条后，平台只保证 `max-height: 40vh`（竖向不撑爆），**21 个导航项横向如何可达（横向滚动 / 「更多」抽屉 / 分组）平台没有给**，必须由 Stage 3 设计；同时请把「折叠后仍能到达全部 21 页」写成可判定验收。
