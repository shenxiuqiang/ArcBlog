## 1. 阶段五步（在总纲 §3 四步之上补"核验"）

```text
① 调研（可并行）→ ② 主笔撰写 → ③ 两路独立审查 → ④ 多轮修订 → ⑤ Lead 核验冻结
```

| 步 | 谁做 | 产出落点 | 停点（必须停下等谁） |
| :-: | --- | --- | --- |
| ① 调研 | 调研员（可多人并行，**一人一文件**） | `docs/08-其他/调研/S<stage>-<n>-<topic>.md` | 主笔取用前不阻塞 |
| ② 撰写 | **唯一主笔**；**先提纲后正文** | `docs/0X-*/_提纲.md` → `docs/0X-*/*.md` | **提纲必须先经 Lead 批准**；每篇写完回报一次 |
| ③ 审查 | 两路**持久 teammate**（产品/架构 + 事实/判据） | `docs/team/reviews/` | 审查者**不改被审文件** |
| ④ 修订 | 主笔（+ 闭合复核） | 正文 + 各篇「变更记录」 | 每条审查意见必须给**采纳/部分采纳/不采纳（写理由）** |
| ⑤ 核验冻结 | **Lead**（不采信自述） | `docs/team/reviews/S*-定稿核验-Lead.md` | **放行后**下一 Stage 才可开写 |

> **与总纲 §3 的差别只有一处**：总纲写"四步"（调研 → 撰写 → 审查 → 修订），本篇把"**Lead 核验冻结**"单列为第 ⑤ 步——因为它是**唯一能宣布定稿的动作**，且 Stage 1–6 每阶段都留下了独立记录（【已实现】：`S1`–`S6-定稿核验-Lead.md` 各 1 份）。

## 2. 阶段门与串行（执行细则）

**两条硬规则**（来源 = 总纲 §2）：

1. **上一 Stage 未定稿，下一 Stage 不得开写**（严格串行）。
2. **定稿 = 三要件齐备，缺一不算**：

| # | 要件 | 判据（可判定） | 落点 |
| :-: | --- | --- | --- |
| 1 | **主笔自检** | 逐条对照该阶段的门（如 Stage 7 = G1–G8），且**可机检条款都带真实输出** | 正文各篇 + 回报消息 |
| 2 | **独立审查通过** | 两路报告的问题**全部处置**（采纳/部分采纳/不采纳 + 理由），且**闭合复核**确认无残留 | `docs/team/reviews/` |
| 3 | **Lead 放行** | Lead 独立复算（不采信自述）+ 冻结快照 sha256 记账 | `S*-定稿核验-Lead.md` |

**门不通过时的动作**（沿用 `AGENTS.md` 铁律 2 的文档线对应形态）：**改回上一冻结版并登记**——本次实战 = Stage 3 触发、登记在 [`S3-定稿核验-Lead.md`](../team/reviews/S3-定稿核验-Lead.md) §3 的跨阶段受控修订。

**Stage 状态**：只以各阶段冻结记录为准，导航见总纲 §2.1（**本篇不复制**该表；表一旦复制就会出现第二处漂移源）。

## 3. 每阶段的交付物与"提纲先行"

### 3.1 过程件与正文件

| 类型 | 路径 | 计入 400 行上限？ | 计入"链接 0 MISS"？ |
| --- | --- | :-: | :-: |
| **提纲**（过程件） | `docs/0X-*/_提纲.md` | 单独上限 **≤200 行** | 是 |
| **正文** | `docs/0X-*/*.md` | 每篇 **≤400 行** | 是 |
| **拆篇** | 超 400 行时拆 `0Xa-…md`，入口仍是 `0X` | 各自 ≤400 | 是 |
| **可执行产物** | 阶段自检脚本（现 `_sens.sh` ×2，见 [`05 §7`](05-文档与代码规范.md)） | 否 | 否 |
| **过程记录** | `docs/team/journal/**`、`docs/team/reviews/**` | 否 | 否 |

### 3.2 提纲先行的四条要求（Lead 批准制）

1. **先提纲后正文**：`_提纲.md` ⊆ 200 行，必须含「文件清单与顺序」「逐篇分节（问题 + 证据来源）」「门」「待裁决」。
2. **批准后才写正文**；批准消息里的裁决（T1–T6 之类）**逐条落章**，未采纳的必须在提纲变更记录里写明理由。
3. **正文与提纲不一致时，以批准后的提纲为准**，或先回报 Lead 变更。
4. **不自行开下一 Stage**；全部篇写完**停下等审查**（本次 Stage 7 的实操）。

### 3.3 阶段日志（journal）粒度

| 规则 | 内容 | 现状 |
| --- | --- | --- |
| 每 Stage **≥1 份** | 内容 = 计划 / 产出 / 审查结论 / 遗留 | 【已实现】Stage 1–2 有 13 份；**Stage 3–6 无日志**（`S7-01 §5-10` 实测） |
| **缺日志 = 阶段门不通过项** | 从 **Stage 7 起**生效 | 【规划中】**不追补** Stage 3–6（已冻结，追补等于制造无证据的过程件） |
| 命名 | `stage-<n>-<nn>-<topic>.md` | 沿用现有形态（例 `stage-2-盖章与stage-3提纲.md`） |

### 3.4 阶段号与调研编号的指定（**Lead 裁决 O1/O2**，2026-09-30）

| # | 项 | 规则 |
| :-: | --- | --- |
| **O1** | 主笔写入范围 glob 里的 `0X` | 由 **Lead 在"开阶段"动作里给定**（阶段任务书 + 冻结记录都写死），本项目 = **用户给定的 8 类顺序**；主笔**不得自定、不得复用**上一阶段的号；新阶段号只在 Lead 的开阶段动作里出现 |
| **O2** | 同一 Stage 追加第二个调研文件 | **允许**，三条约束：① 统一放 `docs/08-其他/调研/`；② 编号 `S<阶段号>-<两位序号>` **递增、不重号**；③ **不得修改已冻结的调研产物**（要纠正就新建一条并注明"更正 `S<n>-<m>` 的 X"） |

> 这两条把 [`00 §2`](00-角色与写入范围.md) 的 glob 从"约定"变成"可判定"：见到 `0X` 先回阶段任务书核号，核不到就是越界。

## 4. 探针与实现轮的分界（**只引用，不重定义**）

探针的**编号、四件（步骤 + 判定式 + 双降级 + 阻塞对象）、批次**唯一定义点 = [`05-开发文档 07`](../05-开发文档/07-未决技术问题与探针计划.md)；功能侧排期 = [`06-功能开发列表 04`](../06-功能开发列表/04-探针与前置门.md)。本篇只定"**谁有权执行**"。

| 类型 | 今天能否跑 | 执行权归属 | 前置 |
| --- | --- | --- | --- |
| **只读探针**（读实例 / 读 HTTP / 读渲染 DOM） | ✅ 只需白名单放行 | 调研员或主笔 | 白名单 = `read/grep/ls/wc/test -e`、`arc dsl validate --json`、`.actions/{list,read}`、`arc <cmd> --help` |
| **需写权限探针**（改 `.aup` + 重启复挂 / 换 topology / 登录会话 / 真资金） | ❌ 本阶段不跑 | **实现轮**（Dev 或平台探针职能位） | 持 `docs/team/.gate-lock`；一次一个；跑完**回滚源码**并重跑门 |

**执行纪律五条**（来源 = `05-开发文档 07 §3`，本条只回指）：① 一次探针 = 一个可回滚的改动；② 写实例串行（先锁后跑）；③ 禁止在生产集合留探针记录（只写隔离路径 / 隔离实例）；④ **回填义务**（跑完必须把该条从【未验证】改成四大标签之一并写证据）；⑤ 不得据未验证项下结论。

> **本阶段立场**：Stage 7 **不执行**任何需写权限的探针（写范围只有 `docs/07` + `journal`），只规定执行权与登记处。

## 5. 安全阀（**本阶段首次定义**；Lead 裁决 T3）

归档期没有这条原文（`S7-01 §3-9` 实测 `grep 安全阀\|上下文预算\|换人` = 0）；最近证据是 `S1-事实审查-Lead复核 §四`。本项目**已实战两次**换人，故上升为条文。

### 5.1 触发条件（满足任一即启动）

| # | 触发条件 | 判据 |
| :-: | --- | --- |
| 1 | **主笔上下文预算耗尽** | 主笔自判"再写会写浅"，或工具调用开始重复/丢失已确认结论 |
| 2 | **连续两轮无实质产出** | 连续 2 次回报无新增文件、无新增证据 |
| 3 | **主笔主动判断"再写会写浅"** | 与 #1 同源，但**允许在还能写好时主动停手**（这是正解，不是失败） |

### 5.2 交接物三件（**缺一不算交接**）

| # | 交接物 | 形态 | 本次实证 |
| :-: | --- | --- | --- |
| 1 | **已落盘半成品** | 提纲 + 已冻结篇 + 调研，全部是文件 | Stage 5 前四篇（`00`–`02a`）由 `doc-owner` 落盘后交接 |
| 2 | **续写登记** | 写清"谁写了哪几篇、哪几篇未写、口径基线是什么" | `S5-定稿核验-Lead.md` 头部「**作者交接**」行 |
| 3 | **新主笔必须回仓库校验前任的数字** | 不照抄前任的任何计数；用 `ls`/`wc`/`grep` 复测 | 【已实现】**两次**：`doc-owner → dev-doc` 接手后抓出 `00:81` 页面计数错（26 → 实测 **30**）；`dev-doc → doc-std` 接手后抓出 `reviews` 20 → **27**、`journal` 13 → **14** |

### 5.3 登记处与反向纪律

- **登记处**：该阶段冻结记录（`S*-定稿核验-Lead.md`）+ `docs/team/journal/` 一份交接日志。
- **反向纪律**：安全阀**不是**"写不完就换人"的借口——换人成本高，**能自己写好时不许换**；交接必须**先落盘再叫人**（`S1-事实审查-Lead复核 §四` 的原始口径："报告先落盘再加结论"）。
- **两次实战**：① `doc-owner → dev-doc`（Stage 5 中途；换人后数字口径 30/14/8 两段完全一致，独立审查确认"没有另起一套"）；② `dev-doc → doc-std`（Stage 7 开工前，即本文档的主笔变更；新主笔回仓库复测抓出 `reviews` 20 → **27**、`journal` 13 → **14**）。
