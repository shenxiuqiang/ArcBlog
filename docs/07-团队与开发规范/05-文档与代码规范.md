## 2. 行长与计数口径（**本项目踩过三次的坑**）

### 2.1 规则

| 项 | 口径 | 实现 |
| --- | --- | --- |
| **版本行** | ≤ **80 字符** | 头部的 `| 版本 | … |` 行 |
| **普通单行** | ≤ **800 字符** | 全文（含表格行） |
| **单位** | **字符**，不是字节 | **`python3` 的 `len(str)`** —— **禁止 `awk length`**（BSD awk 按字节） |

### 2.2 坑的真实形态（**本轮真跑**）

同一个"行长"在两种实现下差一倍：

```bash
$ python3 -c "import io;print(len(io.open('_docs/ArcBlog-feature-checklist.md',encoding='utf-8').read().split('\n')[121]))"
761
$ awk 'NR==122{print length($0)}' _docs/ArcBlog-feature-checklist.md
1384
```

⇒ 该行 **761 字符 / 1384 字节**：`awk` 会把它误判为"超 800 行"（**假红**）。中文 3 字节/字，误差随中文比例放大——本项目在 Stage 2、Stage 5、Stage 6 各踩一次（`S7-01 §4-8`、`S6-02 DOC-05`）。

### 2.3 判据 + **变异必红**

```bash
$ python3 - <<'PY'
import io, glob
over = [(p.split('/')[-1], i+1, len(l))
        for p in glob.glob('docs/07-团队与开发规范/*.md')
        for i, l in enumerate(io.open(p, encoding='utf-8').read().split('\n'))
        if len(l) > 800]
print("over800(字符口径) =", len(over), over)
PY
over800(字符口径) = 0 []

$ python3 -c "open('/tmp/s7c/docs/07-团队与开发规范/00-角色与写入范围.md','a',encoding='utf-8').write('x'*900+'\n')"
$ python3 - <<'PY'   # 同一判据，root 换 /tmp/s7c

PY
正本 over800 = 0 []

```

## 3. 五类标签的用法（**唯一出处 = 总纲 §4，本篇只讲怎么用**）

| 标签 | 必须给什么 | 用错会怎样 |
| --- | --- | --- |
| 【已实现】 | **文件:行** / 命令输出 / AFS 记录 | 空挂 ⇒ 与"已验证"混淆 |
| 【规划中】 | 目标 Stage / 需求编号 | 无落点 ⇒ 变成空承诺 |
| 【平台边界】 | `arc` 实测输出 + **降级路径**（引 [`05-开发文档 02`](../05-开发文档/02-平台能力与边界.md) 对应节） | 把"没 opt-in"写成"平台不支持"（Stage 3 Q7 翻案过） |
| 【决策待定】 | **候选 A/B + 需要谁拍板** | 与【未验证】混用 ⇒ 把"没拍板"当"不知道" |
| 【未验证】 | **未验证什么 + 为什么现在验不了 + 验证方法/判定式** | 把"未验证"当"已知"⇒ 归档期最贵的事故 |

**四条纪律**

1. **【未验证】≠【决策待定】**：前者 = 事实还不知道（需一次探针）；后者 = 事实已清楚但选择未拍板（需人裁决）。
2. **【未验证】≠【平台边界】**：不得升级成"平台不支持"，也不得降级成"大概可以"。
3. **凡【未验证】必须同时写出验证步骤与判定式**；验证完成后**立刻**改成四大标签之一并留证据（"跑过 ≠ 写回"，[`03 §4`](03-质量门与命令手册.md)）。
4. **未验证清单的唯一定义点 = [`05-开发文档 07 §1`](../05-开发文档/07-未决技术问题与探针计划.md)**；其它篇只**回指编号**，不复制四件。

> **落地形态**：每篇头部下方放一张「**事实标签对照**」表（五类各一行，写清"本篇用在哪里"）——这就是"五类标签齐"的可判定形态，也是本目录 7 篇的统一做法。

## 5. 唯一出处与 "grep 确认"（Lead 更正记录的直接教训）

| 例 | 谁 | 原口径 | 更正为 | 怎么发现 |
| :-: | --- | --- | --- | --- |
| 1 | **Lead** | 六态词表唯一出处 = `02-需求 00a` | **= `02-需求 00 §4.2`**（`grep 六态` 在 `00a` **零命中**） | 主笔引的是 `00 §4.2`；Lead 回仓库核原文后确认**主笔对、Lead 错** |
| 2 | **Lead** | Stage 5 待盖章 = "10 篇 + `_提纲`" = **11** | **10 个文件** | 主笔**拒绝照抄**并给出 `ls` 计数，Lead 采纳 |

**操作口径（三步）**

1. **指定唯一出处前**：`grep` 目标词在该文件里**确有命中**（写清命中行/节号）。
2. **落笔时**：写"唯一出处 = X §Y"，并**给出该节的锚点**（节号，不写行号——见 §6）。
3. **发现上游说错时**：**按原文写**（不迁就口头口径）+ **回报**（谁、哪句、原文是什么），由 Lead 决定是否开受控修订。

> 反面模式：**"权威 = <某份材料>"整体声明**。Stage 4 曾用它压过一处分歧，`S4-定稿核验` §2-7 已**删除该声明**，改为"**以可复现为准 + 差异逐条给性质**"。口头的权威指定**不算证据**。

### 6.2 引用格式（**消费者命名**）

统一写 `<阶段文件>:<ID>`，例：

- `03-模式:M09`（Stage 3 的交互模式）
- `04-流程:C1`（Stage 3 的跨页契约）
- `04-UI:S05`（Stage 4 的 UI 条款）
- `05-开发:01 §6`（Stage 5 的篇与节）

**实测反例（规范行自身教错）**：Stage 5 统一命名时，**示范行**把 Stage 4 的 `S0x` 挂在 `03-模式:` 前缀下（**6 处**）⇒ [`S5-定稿核验-Lead.md §2`](../team/reviews/S5-定稿核验-Lead.md) 裁决"**规范行自身必须先正确**"。⇒ **写示例时，示例必须自己先符合规范**，且示例与规范**一起被审**。

## 8. 文档变更记录

| 规则 | 内容 |
| --- | --- |
| 版本号 | `v0.1`（草稿）→ `v1.0`（定稿）；**定稿后每次改动 +0.1**，并在文末「变更记录」加一行（日期 / 版本 / 变更） |
| 变更行写什么 | 改了**哪几节**、**为什么**（依据）、影响的下游 |
| 受控修订 | 除变更行外，**另进**该阶段冻结记录 §1.1（`改 → 报 sha256 → Lead 批准 → 回填 §1 快照 + §1.1 + 升版本`，[`02 §7.2`](02-独立审查与冻结纪律.md)） |
