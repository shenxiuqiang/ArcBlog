## 1. 两路独立审查（默认形态）

| 路 | 问什么 | 不许问什么 | 本次实际形态 |
| :-: | --- | --- | --- |
| **产品/架构路**（pm 类） | "**该不该这样**、有没有兑现上游承诺"：可追溯、边界、无断链、明确不做的项 | 不判"文笔好不好" | `S1-产品审查`、`S2-产品审查`（+复审）、`S3-产品审查`、`S4-产品审查`、`S5-产品审查`、`S6-产品审查` |
| **事实/判据路**（qa 类） | "**每句话有没有证据**、判据能不能红、有没有臆造平台能力" | 不重写正文 | `S1-事实审查`、`S2-事实审查`（+qa 复核+闭合复核）、`S3-事实审查`（+闭合复核）、`S4-事实审查`、`S5-事实审查`（+闭合复核）、`S6-事实审查` |

**硬规则**

1. **两路都要有，且各自是独立的一份报告**；缺一路不定稿（总纲 §2 的定稿三要件第 2 条）。
2. 审查者必须给 **`文件:行` / 命令输出 / 明确的反例**；**不接受"更好""更完善"**（总纲 §3）。
3. **UI 职能位并入审查侧**：视觉/交互条款由审查者按 [`04-UI设计规范`](../04-UI设计规范/) 条款库判，不单独开写范围（[`00 §1`](00-角色与写入范围.md)）。
4. 审查报告落 `docs/team/reviews/`，文件名 `<Stage>-<路>审查.md`（复审/闭合复核加后缀）。
5. 主笔对每条意见必须给 **采纳 / 部分采纳 / 不采纳（写理由）**——**不允许静默丢弃**（总纲 §3）。不采纳的理由要能在报告里被复核。

> **反例警示（内部证据优先）**：Stage 1 两轮审查结论**互斥**（第一轮"放行" vs 第二轮"P0=2"），Lead 最后用**篇内自相矛盾**（`01 §6.1` vs 同篇 `§7.2 B8`）独立判定，而不是在两名审查者之间"选边"（[`S1-定稿核验-Lead.md`](../team/reviews/S1-定稿核验-Lead.md) §3 D1）。

## 2. 评审者不改被审文件 + 审查期冻结窗口

### 2.1 写范围互斥（可判定）

审查者的可写 glob **只有** `docs/team/reviews/**`（[`00 §2.1`](00-角色与写入范围.md)）。判据：审查期间对被审目录的 `git status --porcelain` 必须**只**出现 `docs/team/reviews/` 下的文件。

### 2.2 冻结窗口与"基线"三件

| # | 要求 | 判据 |
| :-: | --- | --- |
| 1 | 报告必须带**基线 sha256** | 对该轮被审文件逐个 `shasum -a 256`；**逐字节**记录 |
| 2 | 报告必须带**时刻** | 形如 `2026-09-30T11:07Z`；结论**只对该快照成立** |
| 3 | 快照改变 ⇒ 结论**失效** | 要么重跑，要么在报告里**显式声明失效**并指出改了什么 |

### 2.3 为什么必须这样做（教训 9 的实证）

| 现象 | 证据 |
| --- | --- |
| 审查期间被审文件**持续被改**（11:07 → 11:09 三次改动），两方结论对不上快照 | `S2-产品审查-复审` 记录"审查期间被另一路写者持续改动"；`S7-01 §4-9` |
| 结论互斥无法收敛 | 见 §1 末的反例警示 |
| 冻结快照与仓库不一致（hash/行数未回填） | [`S1-定稿核验-Lead.md`](../team/reviews/S1-定稿核验-Lead.md) §1：`00-导读.md` 记 `cdfe45d7…`（110 行），实测 `2533aa7e…`（**111 行**） |

> **操作口径**：主笔在收到"审查开始"的通知后**停止写入被审目录**；确需修必须走 §7 的受控修订路径，并**重报 sha256**（这一步在 Stage 1 走过：改一处也升版本）。

## 3. 判据要有判别力（**两个独立要求**）

### 3.1 "能红"与"不假绿"是两件事

| 要求 | 含义 | 怎么证 |
| --- | --- | --- |
| **能红** | 判据对**已知坏样本**必须报错（回滚/变异副本必红） | 造一个反例副本 → 同一条判据 → 必须 FAIL |
| **不假绿** | 判据对**空输入/退化输入**不能报 PASS | 空目录 / 空表 / 全空值 ⇒ 必须 `ENV-ERROR` 或 FAIL |

**本条源自一次真实事故**：`_sens.sh` 的正本绿 + 反例红都成立，但 qa 追加发现**空目录扫描会假绿** ⇒ 现在有**样本下限断言**：扫描到 `<30` 个文件即报 `ENV-ERROR`（[`S4-定稿核验-Lead.md`](../team/reviews/S4-定稿核验-Lead.md) §4-1）。**"判据能红"与"判据不会假绿"是两件事**——只做前者会漏掉一整类假 PASS。

### 3.2 Stage 6 的实证：三条判据里两条抓不到明天会漏

| 旧判据 | 缺陷（变异已证） | 新判据 |
| --- | --- | --- |
| G4 = `id in body`（字符串命中） | 删掉某 id 的**唯一落点行仍 PASS**——区间写法（`GATE-01…07`）一句覆盖整族 | **逐行可定位**（id 必须落在某行首列/来源列，单元格与 id 相等）；`locatable == 65`；**"区间句不算落点"** |
| G8 只查 2/6 态 | ① `§4` 曾允许"状态格写 `无证据`" ⇒ 不在六态内 ⇒ **整行隐形（假 PASS）**；② 22 行不受任何证据检查 | ① `§4` 改"状态格仍写六态之一、`无证据` 写证据格"；② 状态格非六态 ⇒ **直接红**；③ 扩到**全 6 态**并按态设期望 |
| G1 = 集合比较 | 曾写成 `fp == matrix`（`FP-` 集合 vs `PRD-` 集合，**永不可能相等**） | 改 `prd == matrix` + `len(fp) == 50` + `dup_fp` |

**Lead 亲手复现的变异（真实输出，来自 [`S6-定稿核验-Lead.md`](../team/reviews/S6-定稿核验-Lead.md) §3）**：

```text
# 在 /tmp 副本删掉 02 的 ENG-01 行（GATE-01 的唯一落点）后重跑 G4
s6-02 ids 65 locatable 64
missing 1 ['GATE-01']
VERDICT FAIL
```

> **纪律**：可机检判据**必须附一条变异/回滚用例**；**只给正本绿不算成立**。"判据能力边界"（能抓什么 / **不能抓什么**）必须写在判据旁边——`S6/00 §6` 明写"**它不能验证证据为真**"，正因如此 `已验证` 必须由**独立方**给出。

### 3.3 三条实现细则

| # | 细则 | 反例（实测） |
| :-: | --- | --- |
| 1 | **整块解析，禁窗口截断** | 判据用 **400 字符窗口**取头行内容 ⇒ 窗口落在头行外 ⇒ 记 `C03 = 2`，**真值 0**（假阳性，`S4-定稿核验` §2-7） |
| 2 | **逐条目判据**，"出现即通过"不算 | Stage 2 因"出现即通过"漏抓 `01-CNT` 的节标签错位；改为按 `### 3.x PRD-…` 切块核 8 节**齐全与顺序** |
| 3 | **差异逐条给性质**，不得整体归因 | 不得写"统计单位不同"一句话带过；须逐格重算并给每格的性质（假阳性/注释口径/调研记录错误/页 vs 处） |

## 4. 分歧先怀疑自己的判据，再怀疑对方的数据

**Stage 4 的真实反转**：主笔把"我的粗判 vs 调研脚本不一致"当成**单位差**，并声明"以调研为准"；qa 逐格复算证明是**判据假阳性**（真值 0）。⇒ 结论从"调研错"翻成"我的判据错"（[`S4-定稿核验-Lead.md`](../team/reviews/S4-定稿核验-Lead.md) §2-7）。

**操作口径**：出现分歧时，**先重算自己的判据**（换方法、换实现、看全部输入），再要求对方给原样输出；**禁止**用"权威 = <某份材料>"一句话整体定案。

> 这条与 [`05 §5`](05-文档与代码规范.md) 的"唯一出处必须回原文 grep 确认"是同一族纪律：**口头的权威指定不算证据**。

## 5. 闭合复核不可省

| 项 | 内容 |
| --- | --- |
| **只做什么** | 专验"**已提出的问题是否闭合** + **修复是否引入新缺陷**"，**不做全量重审** |
| **输入** | 前一轮问题清单 + **当前**快照（sha256） |
| **输出** | 三分类计数：`closed / partial / new`，逐条给证据 |
| **实证** | [`S3-事实审查-闭合复核.md`](../team/reviews/S3-事实审查-闭合复核.md)：**6 closed / 3 partial / 4 新缺陷**；Stage 2 与 Stage 3 的闭合复核各再抓出 **2–4 条**"主笔声称已修"的残留 |
| **为什么不可省** | 主笔的"已修"是**自述**；闭合复核是唯一能证伪它的动作（教训 2：主笔在 `00:202` 声称判据已加敏感性，闭合复核证明"四个判据**代码一字未改**"） |

**强制**：闭合复核报告必须与两路审查报告**分开归档**（文件名含 `闭合复核`），且必须给**未闭合项的处置**（改 / 转遗留 / 升级为待裁）。

## 6. 持久 teammate、迟到材料与 **Lead 代行**（Lead 裁决 T2）

### 6.1 用持久 teammate，不用一次性子智能体

动因（【已实现】）：Stage 1 派出 **5 名**审查/调研子智能体，其中 **2 名**未在约定时间交付（后迟到），且 `send_message` 对子智能体**不可达**（"active teammate not found"）⇒ 对策 = **审查用持久 teammate**（`pm`/`qa` 形态），可被 Lead 唤醒与追问（`S2-定稿核验` §4-1、`S1-事实审查-Lead复核` §四）。

### 6.2 迟到材料：先报 Lead、只做只读分析

| 步 | 动作 |
| :-: | --- |
| ① | 收到迟到材料 ⇒ **先报 Lead**，说明"基于哪个快照、与现行版本差在哪" |
| ② | **只做只读分析**，**不采信其结论、不改正文** |
| ③ | 由 **Lead 决定**是否开修订轮；需要修时走 §7 受控修订路径，避免出现**两条并行版本线** |

来源 = Stage 1 裁决 D3（主笔在"停下等放行"期间自行处理迟到材料被判**追认 + 设规则**）。

### 6.3 Lead 代行补位（**允许，但三条强制 —— 每条都有落点与判定式**）

| # | 强制项 | 落点（写在哪） | 判定式（怎么判，可复制） |
| :-: | --- | --- | --- |
| 1 | Lead 代行时，审查报告**必须标注**「**独立性：Lead 代行**」 | 该份**审查报告**头部字段（`§8` 模板的 `| 独立性 |` 行） | 报告内 `grep -c '独立性'` ≥ 1 且其值 ∈ {`独立`, `Lead 代行`}；代行而写"独立" ⇒ **违规** |
| 2 | **代行不改变"两路独立审查"的要求**：某一路失约时 Lead **只补位**，且定稿记录里必须写明"**哪一路由 Lead 代行**" | 该阶段**定稿核验记录**的「**审查链**」行（`§7.1` 一等字段；模板见 §8.2） | 该行必须写明两路各自的**路名 + 执行者 + 是否代行**；只要发生过代行，`grep -c '代行' S*-定稿核验-Lead.md` ≥ 1；**未发生代行时必须显式写"两路均独立"**（不得留空） |
| 3 | 该阶段的**放行结论必须同时有**：**另一路独立审查** + **Lead 自己的核验记录** | 定稿核验记录的「审查链」行 + 「Lead 独立核验」节 | 判定式：① 至少 **1 份** `docs/team/reviews/<Stage>-*审查.md` 的「独立性」= `独立`（即**至少有另一路没代行**）；② 定稿记录含非空的「Lead 独立核验」节（列核验项 / 方式 / 结果） |

**边界与兜底（补 pm 的第四点）**

| 情形 | 规定 |
| --- | --- |
| **两路同时失约** | **Lead 只能补一路** ⇒ 剩余一路**必须等外部审查者**；**不得放行**（冻结不发生），升级**人类**裁决 |
| 强制 3 的"另一路"若也是代行 | **不放行**（等于没有独立审查） |
| 历史记录（规则生效前，如 Stage 1） | **追认**：不改历史结论，只补标注（「审查链」行标"事实审查由 Lead 代行"）；**由 Lead 在 reviews 写范围**内执行（主笔无权改 `docs/team/reviews/**`） |

**实证与代价**：Stage 1 的 `S1-事实审查-Lead复核.md` 就是这样产生的，Lead 在报告里**自认独立性弱于理想态**（`:76`，散文形式——**当时规则未生效**，`S1-定稿核验-Lead.md:8` 的「审查链」行也**未**写代行）⇒ 这正是本条要修的漏洞。代行是**兜底**，不是常态；能用持久 teammate 就不用代行。

## 7. 冻结与受控修订路径

### 7.1 冻结快照（Lead 记账）

| 项 | 要求 |
| --- | --- |
| **审查链（一等字段，R1/R7）** | 首字段，一行写全：**两路各自的「路名 + 执行者 + 独立性」**（例：`产品/架构路 = pm（独立）｜事实/判据路 = qa（独立）`；发生代行时写 `… = **Lead 代行**`）。**不得留空**；未发生代行时显式写"两路均独立" |
| 形态 | 逐文件一行：`<sha256>  <文件名>  (N 行)`，放进 `S*-定稿核验-Lead.md` §1 |
| 可复核 | **必须能被一次 `shasum -a 256` 复核通过**；行数用 `wc -l`（**字符口径**无关，行数即行数） |
| 语义 | 本节 = **最新受控修订后**的状态；v1.0 原始快照另存一行供追溯（[`S1-定稿核验`](../team/reviews/S1-定稿核验-Lead.md) §1 的做法） |
| 变更史 | 逐条改动的表放 **§1.1**，字段 = 日期 / 文件 / 版本 / 内容 / 依据 |
| 遗留 | 「遗留」节：逐条给**去向**（实现轮 / Stage 6 `ENG-*` / 人类裁决） |
| 模板 | 见 **§8.2**（定稿核验记录模板）；**历史 6 份不追改**（节次命名各异，只对**新阶段**生效） |

**教训 13（必须防住）**：Stage 1 的 v1.2 只回填了 §1.1，**没有更新 §1 的 hash/行数** ⇒ 快照节与仓库不一致（`cdfe45d7…`/110 vs 实测 `2533aa7e…`/111）。
⇒ **受控修订的登记动作 = 改文件 + 重算 sha256/行数并回填 §1 + 写 §1.1 + 升版本 + 变更记录行**，**五件缺一不可**。

### 7.2 受控修订路径（冻结后唯一合法改动）

```text
改（主笔或 Lead，只允许"事实对齐"）
  → 回报 sha256（新值 + 同源 grep 结果）
  → Lead 批准
  → 回填该阶段冻结记录 §1.1（+ §1 快照）
  → 升版本 + 正文「变更记录」加一行
```

| 约束 | 内容 |
| --- | --- |
| **只允许事实对齐** | 禁止借受控修订**扩范围、改口径、加条款**；改口径必须走新的裁决并另行登记 |
