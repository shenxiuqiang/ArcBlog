## 1. 背景

`spec §142` 规定 **ArcBlog Network 不应该存在唯一官方 Hub**：官方可以运行一个 Hub，但它只是 **One Hub**，不是 **The Hub**。`03 §7（J7 平台方）` J7-3 把"治理承诺"列为平台方旅程的一步，但**现状没有任何可执行的检查项**（`S2-01 §3.2` 断链②把"治理承诺"列入"有承诺无落点"）。

同时，平台实测（`R3 §2.6`）确认：**root 级 HTTP 发现端点不可达**，跨节点核验只能逐节点读 AFS。这决定了本清单**只能**由"单节点可得事实 + 人工汇编"构成，**不能**设计成网络级对账服务。

## 2. 选项

| 选项 | 内容 | 优点 | 缺点 |
| :-: | --- | --- | --- |
| **A（采纳）** | 产出一份**可断言的清单**，每条都能被判"通过/不通过"，落 `docs/08-其他/决策/` | 可执行、可被 Stage 7 复检；不依赖不存在的网络级接口 | 需人工逐节点执行 |
| B | 不做清单，只在 `PRD-NET-07` 里写原则 | 成本低 | 归档期"应当独立"这类**不可判定**表述已被证明会被反复引用而无从验证 |
| C | 造一个跨节点对账服务 | 自动化 | 平台不支持（`R3 §2.6`），属承诺不可达能力 |

## 3. 裁决（采纳 A）

**治理清单（每条必须可判"通过/不通过"）**

| # | 断言 | 判据（单节点可得） | 反例 |
| :-: | --- | --- | --- |
| G1 | 官方 Hub 不是唯一入口 | 任一 Studio 的 `hub/registrations/` 中**存在 ≥2 个不同 Hub DID**，且其中至少 1 个 ≠ 官方 Hub DID | 只有官方一个 Hub 即不通过 |
| G2 | Hub 互为独立单元 | 移除任一 Hub 关系后，其余 Hub 的关系行**仍为 `indexed`**（互不阻塞） | 任一 Hub 失败导致其它关系不可用 |
| G3 | 实例数据可导出/可搬迁 | `AFS:node/*`、`posts/`、`drafts/` 三处记录可逐条读出（`arc afs exec …read` 成功）且不依赖写入方在线 | 记录只能经某一节点服务访问 |
| G4 | 角色资格不是"官方认证" | `node/factories.json` 中 `nodes.*.adapter` 为 `ocap\|mock` **三态如实标注**；mock 不得写成 `simulated: false` | 把 mock 事实渲染成链上已验证 |
| G5 | 发现面不依赖 root 级端点 | `transport: ["afs","mcp"]` 声明为真，且不存在任何"根路径 API 可得"的页面/文档表述 | 文档声称 `/.well-known/arcblog` 可用 |

## 4. 依据

- `spec §142`（不应存在唯一官方 Hub）、`§141`（软件 ≠ 网络）、`§143`（官方 Hub 只是其中之一）。
- `R3 §2.6`：root 级 HTTP 端点不可达 ⇒ 核验形态必须是 AFS-native。
- `R3 §4-5`：mock 不得声称"链上已验证"（G4 的依据）。
- `S2-01 §5 O6` 与 `03 §12.2（已裁决）`：过程性台账与治理清单归 `08-其他`，PRD 保持单一职责。

## 5. 影响

| 对象 | 影响 |
| --- | --- |
| `PRD-NET-07` | 需求只**引用**本文件（§9），不复述清单正文 |
| Stage 5（开发文档） | 平台边界篇需登记"网络级核验不可达"及其降级路径 |
| Stage 7（团队与开发规范） | 本清单可作为**治理复检项**（人工，非自动门） |
| 根 `README.md`（Stage 8） | 可引用 G1 说明"官方 Hub 只是一个 Hub" |

## 6. 何时回看

| 条件 | 动作 |
| --- | --- |
| 平台开始支持 root 级自定义 HTTP 端点 | 可评估把 G1/G2 自动化（当前**禁止**据此设计需求） |
| 出现第二个官方运营的 Hub | G1 的判据需重新表述（避免把"官方"当成单一 DID） |
| Stage 7 建立治理门 | 本清单转为门的一部分，并补机检命令 |
